## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5, `docs/specs/SPEC.md` §12.8 y §12.17 (ticket 3
de Bloque A). Depende de TSK-095 (`hero_pool` ya con `accountId`). Hoy `buildMetaSnapshot(db)` lee
`hero_pool`/`settings` sin ningún filtro y `getCachedMetaSnapshot` cachea **un único** `MetaSnapshot`
en un singleton de módulo — con multi-cuenta, el pool de un usuario se filtraría a todos los demás.
Este ticket es un cambio **mecánico de firma**, sin comportamiento nuevo visible todavía (nadie
pasa un `accountId` real hasta TSK-098) — va solo, sin mezclarse con lógica de auth, mismo criterio
que ya usó el proyecto en TSK-045/TSK-047 (Fase 3).

## Alcance — 2 archivos

### 1. `apps/engine/src/meta/provider.ts`
```ts
export type AccountId = number; // Steam32

export async function buildMetaSnapshot<TSchema extends Record<string, unknown>>(
  db: Db<TSchema>,
  accountId: AccountId | null,
): Promise<MetaSnapshot>

export async function getCachedMetaSnapshot<TSchema extends Record<string, unknown>>(
  db: Db<TSchema>,
  accountId: AccountId | null,
): Promise<MetaSnapshot>

export function invalidateMetaSnapshotCache(): void;              // sin cambio de firma
export function invalidateAccountMetaCache(accountId: AccountId): void;   // nueva
```
**`accountId` es obligatorio, no opcional con default** — un parámetro `accountId?: AccountId |
null = null` dejaría que un llamador nuevo que se olvide de pasarlo obtenga silenciosamente "sin
pool" (mismo tipo de bug que dejó `hero_pool_fit` inerte desde 1b hasta TSK-064). Que no compile es
la funcionalidad.

Cache partido en dos capas:
```ts
let sharedSnapshot: SharedMetaSnapshot | null = null;               // heroes + matchups + patchStats
const accountOverlays = new Map<AccountId, AccountMetaOverlay>();   // hero_pool + baseline, por cuenta
```
`getCachedMetaSnapshot` compone `{ ...shared, ...overlay(accountId) }`, devuelve un `MetaSnapshot`
con la forma exacta de hoy — **ningún consumidor cambia** (`buildSuggestions`, las señales,
`RAW_RANGE`, los pesos). `invalidateMetaSnapshotCache()` sigue invalidando solo `sharedSnapshot`
(se llama al final de `runMetaSync`, sin cambios). `invalidateAccountMetaCache(accountId)` borra
solo `accountOverlays.delete(accountId)` — nunca el mapa entero.

`accountId: null` → `heroPool: []`, `personalBaselineWinrate: null` → `hero_pool_fit` devuelve
`applicable: false` (camino ya especificado en §9.3, con candado de regresión propio — confirmar
que sigue pasando, no reescribirlo).

## Casos a probar
1. Dos llamadas con `accountId` distinto sobre la misma `sharedSnapshot` (mockeada/inyectada)
   devuelven overlays distintos — aislamiento verificado a nivel de función, no solo de query.
2. `invalidateAccountMetaCache(X)` no afecta el overlay cacheado de la cuenta `Y`.
3. Invalidar tras una sync de meta (`invalidateMetaSnapshotCache`) fuerza releer `sharedSnapshot`
   pero **no** borra ningún overlay — un segundo `getCachedMetaSnapshot(db, X)` inmediato reusa el
   overlay de `X` sin recalcularlo.
4. `accountId: null` → `heroPool: []`, `personalBaselineWinrate: null`.

## Fuera de alcance
- Ningún llamador pasa todavía un `accountId` real de usuario logueado (TSK-098/TSK-099).
