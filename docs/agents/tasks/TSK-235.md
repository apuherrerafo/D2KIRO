## Contexto

`.github/workflows/ci.yml` filtraba `push` y `pull_request` sólo a `master`. Los PRs hacia
`staging/private-beta-1` (#13, #14, #15) no corrían GitHub Actions: dependían de los gates locales
(`verify-simplicity.sh`, `bun run test`) y de Greptile. Es el único bloqueante técnico abierto antes
del freeze humano F0 de Party Intelligence (Fase 11, `TSK-220`→`TSK-234` reservados — este ticket
usa el siguiente ID libre, `TSK-235`).

## Alcance (mínimo, a propósito)

Sólo los filtros de rama de los dos triggers que ya existían:

```yaml
on:
  push:
    branches: [master, staging/private-beta-1]
  pull_request:
    branches: [master, staging/private-beta-1]
```

**No cambia**: jobs, matriz, comandos de prueba, permisos, secretos, ni nada de despliegue. No se
agrega job de deploy — Railway sigue siendo el único responsable del auto-deploy de staging.
`master` y producción no se tocan (el PR va a `staging/private-beta-1`).

`write_scope` es sólo el workflow; el propio ticket, `journal.md`, `PROGRESS.md`, `hub.html` y
`ledger.md` ya están permitidos por el hook. Toca además `TSK-219.md` (pasa a `blocked`, ver su
sección "Estado 2026-10-02") mientras `TSK-219` era todavía el ticket en `doing`.

## Criterios de aceptación

1. YAML válido y sin otro cambio semántico que los dos filtros (`git diff` del workflow = 2 líneas).
2. `bash scripts/verify-simplicity.sh` en verde (con `VERIFY_COMMIT_GATE=1` en el camino de commit).
3. **El PR hacia `staging/private-beta-1` dispara GitHub Actions de verdad** — el workflow `CI`
   aparece como check del PR, corren los jobs canónicos (`test` ×3, `verify-simplicity`,
   `intelligence-ci`, `r1-certification`) y terminan en verde. No se infiere del YAML.
4. Merge sólo en `staging/private-beta-1`; Railway despliega solo el SHA exacto del merge y
   `/healthz` responde sano.
