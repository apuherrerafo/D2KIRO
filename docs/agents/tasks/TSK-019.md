## Contexto (ticket autocontenido)
Proyecto: dota2coach. Este ticket implementa la costura **S7** completa: una función pura que
recibe el historial de partidas por héroe de un jugador (ya obtenido por TSK-018) y devuelve una
propuesta de hasta 5 héroes ordenados por comodidad. **Cero red aquí** — la entrada es el array ya
mapeado (`{hero_id, games, win}[]`), la salida es determinista. Se prueba con fixtures en memoria,
nunca contra OpenDota real.

No depende de que TSK-018 esté terminado para empezar (la forma de entrada ya está definida
abajo), pero si TSK-018 cambia esa forma, este ticket se ajusta.

## Algoritmo exacto (§9.4 de `docs/specs/SPEC.md`, no hay margen de interpretación)

Entrada: `heroRows: { heroId: number; games: number; wins: number }[]` (todas las partidas de la
ventana, ya filtradas por fecha antes de llegar aquí — TSK-018 hace el filtro de fecha vía la API,
esta función no vuelve a filtrar por fecha).

1. Descartar héroes con `games < 10` dentro de la ventana (umbral fijo, D9 de `SPEC.md`).
2. `baseline = Σwins / Σgames` sobre **todas** las filas de la ventana — sin filtrar por el mínimo
   de 10, o el baseline sale inflado (los héroes con pocas partidas pero buen winrate se cuentan
   igual en el denominador global).
3. Para cada héroe que pasó el filtro del paso 1, calcular:
   ```
   shrunk = (wins + K × baseline) / (games + K),   K = 10
   ```
4. Ordenar por `shrunk` descendente. Desempate: `personalGames` (== `games`) descendente.
5. Tomar los primeros 5. **"Hasta 5" es un techo, no un piso** — si 0, 1, 2, 3 o 4 héroes pasan el
   filtro del paso 1, la propuesta tiene esa cantidad, nunca se rellena artificialmente.
6. Cada entrada de la propuesta lleva `source: 'calculated'`.

Salida: `{ proposed: HeroPoolEntry[]; baselineWinrate: number; consideredHeroes: number }` —
`consideredHeroes` es el total de héroes en la ventana antes del filtro del paso 1 (para que la UI
pueda explicar "de tus 23 héroes jugados este trimestre, 5 pasaron el mínimo de 10 partidas").

```ts
interface HeroPoolEntry {
  hero: number; // HeroId
  source: 'manual' | 'calculated';
  personalWinrate: number | null; // 0.0 – 1.0
  personalGames: number;
  updatedAt: string;
}
```

Caso borde: cero héroes pasan el filtro → `proposed: []`, `baselineWinrate` igual se calcula (paso
2 no depende del filtro), `consideredHeroes` refleja el total real. No es un error.

## Reglas duras
- Función pura: misma entrada, misma salida, sin `Date.now()` propio (`updatedAt` se inyecta como
  parámetro o lo pone el llamador, no esta función).
- Nunca lanza para entradas válidas (array vacío es una entrada válida → `proposed: []`).
- No trunca a 5 antes del filtro de mínimo — el orden de las operaciones (filtrar → baseline →
  suavizar → ordenar → cortar) es el que importa para que el baseline no salga inflado.

## Aceptación
- Entrada vacía → `proposed: []`, `baselineWinrate` según se defina para el caso sin datos (0 o
  `null` — decidir y documentar en el propio código, no dejarlo implícito).
- Con más de 5 héroes pasando el filtro, se devuelven exactamente los 5 con mayor `shrunk`.
- Con 0 héroes pasando el filtro pero historial no vacío, `proposed: []` y `consideredHeroes > 0`.
- Prueba que verifica la fórmula de `shrunk` con valores conocidos a mano (no solo snapshot testing
  — un caso calculado manualmente que confirme el número exacto).
- Prueba que confirma que el `baseline` se calcula sobre **todas** las filas, no solo las que
  pasan el filtro de 10 partidas (caso donde un héroe de 3 partidas al 100% no debe inflar el
  baseline si se excluyera indebidamente).
