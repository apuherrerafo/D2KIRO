## Contexto

QA de TSK-189: con `usePersonalPool: true` el Copilot del Simulador, del pick 3 al 5, **sólo
mostraba héroes del hero pool** — nada más. El usuario quiere el pool como **señal blanda**
(empuja hacia arriba los héroes con los que juega cómodo dentro de su rol), no como filtro que
tapa el resto.

Causa: hoy hay un **acoplamiento** en `apps/engine/src/server/app.ts` `handleSuggestionsPreview`:

```ts
const auth = body.usePersonalPool && !body.teamOpening ? requireHttpAccount(request) : { ok: true, accountId: null };
```

- El overlay de cuenta (que llena `meta.heroPool`) **sólo se carga si `usePersonalPool: true`**.
- `usePersonalPool: true` **también** dispara el filtro duro de `candidatePool` (`mix.ts:317-320`:
  restringe los candidatos a los del pool).

Resultado: para que `hero_pool_fit` puntúe hay que mandar `usePersonalPool`, y eso trae el filtro.
Todo o nada.

`hero_pool_fit` **no necesita `usePersonalPool`** — activa sólo con `meta.heroPool` no vacío
(`hero-pool-fit.ts:23`): in-pool → boost de comodidad, out-of-pool → `raw: 0.2` (nudge leve, no
oculta). Es exactamente la señal blanda que el usuario quiere.

## Alcance

### 1. Motor — `apps/engine/src/server/app.ts`, `handleSuggestionsPreview`

Desacoplar la resolución de cuenta del flag `usePersonalPool`: si viene un `x-account-token`
(para cualquier fin), se verifica y se carga el overlay; `usePersonalPool` queda **sólo** como el
flag del filtro duro.

```ts
const hasAccountToken = request.headers.get("x-account-token") !== null;
const auth = hasAccountToken || (body.usePersonalPool && !body.teamOpening)
  ? requireHttpAccount(request)
  : { ok: true as const, accountId: null };
if (!auth.ok) return auth.response;
```

- Token presente y válido → `accountId` real → `getCachedMetaSnapshot(db, accountId)` trae el
  overlay → `hero_pool_fit` puntúa.
- Token presente e inválido → `401` (falla ruidosa, correcto).
- Sin token → `accountId: null` (igual que hoy).
- `usePersonalPool` se sigue pasando tal cual a `buildSuggestions` (filtro duro sólo si el
  llamador lo pide explícito — p. ej. la vista de draft en vivo, no el simulador).

### 2. Cliente — `apps/web/features/random-draft-simulator/use-random-draft-session.ts`

En el body del preview, **dejar de mandar `usePersonalPool: true`**. Mantener el header
`x-account-token` (para que el overlay cargue y `hero_pool_fit` vote) y `targetPosition` (filtro
por rol, ese sí lo queremos). Quitar el `usePersonalPool: engineToken !== null && !teamOpening`.

## Criterios de aceptación

1. `bunx tsc --noEmit` limpio en `apps/engine` y `apps/web`. `bun test` verde en ambos, cero
   regresión.
2. **Motor**: `POST /api/suggestions/preview` con `x-account-token` válido y **sin**
   `usePersonalPool` → la respuesta trae `hero_pool_fit` con `raw` numérico (no `applicable:
   false`) y `candidatePool` **no** está restringido al pool (aparecen héroes fuera del pool en el
   rango de posición). Test de `app.test.ts` o equivalente.
3. **Motor**: token inválido → `401` (sin cambio). Sin token → `accountId: null`,
   `hero_pool_fit` `applicable: false` (sin cambio).
4. **Motor**: `usePersonalPool: true` explícito (otra ruta/llamador) sigue aplicando el filtro
   duro — la regresión de la vista de draft en vivo no cambia.
5. **Cliente**: el body del preview del Simulador lleva `x-account-token` + `targetPosition`, **no**
   `usePersonalPool`. Test de integración de `use-random-draft-session` actualizado.
6. **QA manual** en `/simulator`: elegir midlane con pool configurado → el Copilot muestra
   **varios** midlaners (pool y no-pool), con los del pool arriba; el desglose de `hero_pool_fit`
   dice "En tu pool" / comodidad para los tuyos y "Fuera de tu pool" para el resto.

## Fuera de alcance

Cambiar `hero_pool_fit`, sus constantes o su peso en V6. El filtro duro de `usePersonalPool` en sí
(sigue disponible para quien lo pida). El bot. `SPEC.md` no se reabre — es corrección de cableado.
