## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5 + confirmación del usuario (SPEC.md §12.16-2,
confirmada 2026-08-24): "cualquier persona logueada ve/edita los equipos de todas las demás" es
exactamente la misma clase de fuga que esta fase existe para cerrar en `hero_pool`, en otra tabla.
Depende de **todo el Bloque A y B completos** — necesita `accounts` poblada (TSK-094) y el helper
`requireAccount` ya construido (TSK-098) — no puede adelantarse a ningún ticket anterior.

A diferencia de `hero_pool`, **no hace falta cirugía de PK**: `team_groups` ya tiene un `id`
autoincremental propio — el scoping es una columna nueva, no un cambio de clave primaria.
`team_members` no gana columna propia: hereda el scope de forma transitiva vía su `teamGroupId`
existente.

## Alcance — 3 archivos (excepción de migración de CLAUDE.md: schema + migración + queries
afectadas = 1 unidad lógica)

### 1. `apps/engine/src/db/schema.ts`
```ts
export const teamGroups = sqliteTable("team_groups", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  accountId: integer("account_id").references(() => accounts.steamAccountId), // NUEVO
  name: text("name").notNull(),
  partySize: integer("party_size").notNull().$type<1 | 2 | 3 | 5>(),
  updatedAt: text("updated_at").notNull(),
});
```
**Nullable, no `.notNull()`** — mismo criterio que `hero_pool` (`PRAGMA foreign_keys` apagado): la
FK es documentación, el aislamiento real lo da el `WHERE account_id = ?`. Un `NOT NULL` real
exigiría el mismo patrón tabla-nueva/copiar/drop/rename que `0006`, sin beneficio real acá — toda
fila nueva pasa por `createTeamGroup`, que a partir de este ticket exige token válido y siempre
escribe un `accountId` real.

### 2. `apps/engine/src/db/migrations/0007_team_groups_account.sql` (nuevo) + `_journal.json`
```sql
ALTER TABLE `team_groups` ADD COLUMN `account_id` integer REFERENCES `accounts`(`steam_account_id`);
--> statement-breakpoint
UPDATE `team_groups`
SET `account_id` = (SELECT `steam_account_id` FROM `accounts` LIMIT 1)
WHERE (SELECT COUNT(*) FROM `accounts`) = 1;
```
Mismo criterio exacto que `0006` para 0/1/≥2 cuentas. `_journal.json` gana `idx: 7`.

### 3. `apps/engine/src/db/queries.ts` + `apps/engine/src/server/routes/team-groups.ts`
`getTeamGroups(db)` → `getTeamGroups(db, accountId)` con `WHERE account_id = ?`. `getTeamGroup`/
`replaceTeamGroup`/`deleteTeamGroup` (reciben un `id` de fila) pasan a recibir también `accountId`
y verifican que la fila encontrada le pertenezca **antes** de devolver/modificar/borrar — un `id`
válido de otra cuenta responde `404`, **nunca `403`** (no confirma que el recurso existe, mismo
principio que el resto de la API). `createTeamGroup` exige `accountId` como campo obligatorio de la
fila a insertar. Las 5 rutas HTTP ganan `requireAccount` (TSK-098) delante — `/api/team-groups` pasa
de sin auth a exigir `x-account-token`.

## Casos a probar
1. Cuenta A crea un equipo; cuenta B, con `GET /api/team-groups`, no lo ve.
2. Cuenta B intenta `GET`/`PUT`/`DELETE` sobre el `id` del equipo de A → `404` en los tres casos.
3. Migración `0007` con 1 cuenta real: todos los equipos existentes quedan con ese `account_id`,
   mismo conteo antes/después.
4. `createTeamGroup` sin `accountId` (llamada mal formada, por ejemplo desde una ruta que se olvidó
   de pasarlo) → falla de compilación o excepción explícita, nunca inserta una fila huérfana en
   silencio.
5. `/api/team-groups` sin `x-account-token` → `401`, mismo formato de error que `/api/hero-pool`.

## Fuera de alcance

- `team_members` no gana columna propia — confirmar que las queries que lo tocan siguen operando
  vía `teamGroupId`, sin necesitar un segundo `WHERE account_id`.
