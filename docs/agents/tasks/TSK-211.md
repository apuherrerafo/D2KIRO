## Contexto

SPEC.md §16.9. El motor amplía `SignalContribution` (TSK-209) y `Suggestion` (TSK-210); `apps/web`
lo espeja **a mano** — los dos procesos son independientes, nunca un import. Sin este cambio en el
mismo PR, `tsc` de `apps/web` rompe.

## Alcance

1. **`features/draft/types.ts`**:
   - `SignalContribution` gana `normalized: number | null` y `evidenceConfidence: number`
     (opcionales o requeridos según cómo lo dejó TSK-209 en el motor — **espejar exactamente**).
   - `Suggestion` gana `evidenceCoverage: number` y `guessingIndex: number`.
   - Comentario de espejo (mismo criterio que Fase 3 / Fase 4.2).
2. **`features/draft/validation.ts`**:
   - `isSignalContribution`: `(value.normalized === null || isFiniteNumber(value.normalized))` **y**
     `isFiniteNumber(value.evidenceConfidence)`.
   - `isSuggestion`: `isFiniteNumber(value.evidenceCoverage)` **y** `isFiniteNumber(value.guessingIndex)`,
     ambos en `[0, 1]`.
3. **`SignalBreakdown.tsx` NO se toca** — sin cambio visual en 9.1 (D4). `normalized`/`guessingIndex`
   quedan disponibles en el tipo para un follow-up de UI.
4. **`bot-drafter.ts` NO se toca** — no consume `SignalContribution`.

## Criterios de aceptación

1. `validation.test.ts`: un `SignalContribution` sin `normalized`/`evidenceConfidence` (si el
   motor los dejó opcionales) sigue validando; uno con `normalized: "x"` o
   `evidenceConfidence: NaN` → inválido. Un `Suggestion` con `evidenceCoverage: 1.5` → inválido.
2. `bunx tsc --noEmit` limpio en `apps/web` **con** el motor ya en la forma de TSK-209/210.
3. `bun test apps/web` verde; ninguna suite existente cambia de resultado salvo `validation.test.ts`.
4. `git diff --name-only`: sólo los 3 archivos del `write_scope`.

## Fuera de alcance

Renderizar `guessingIndex` / `normalized` en la UI (follow-up post-QA, D4).

`bunx tsc --noEmit` (apps/web) + `bun test apps/web` + `verify-simplicity.sh`. **`@redteam`
