## Contexto (ticket autocontenido)
Proyecto: dota2coach — `apps/web/components/signal-breakdown/SignalBreakdown.tsx` ya muestra las 4
señales de fase 1 (`SIGNAL_LABELS`, una fila por señal, incluidas las que dan `raw: null` — nunca
se calla una señal sin dato). `apps/web/features/draft/types.ts` define `SignalId` y
`SignalContribution` en espejo del motor. Este ticket es el último de fase 1b: hace que la UI
refleje la quinta señal que el motor (TSK-022/023) ya calcula y envía por WebSocket.

**Depende de TSK-022 y TSK-023** (la señal debe existir y estar wireada en `mix.ts` para que haya
algo real que mostrar) — aunque la UI en sí puede construirse y probarse antes con datos fijos.

## Cambios exactos

**1. `apps/web/features/draft/types.ts`** — extender el tipo, mismo patrón que el motor:
```ts
export type SignalId = "counter" | "patch_meta" | "team_synergy" | "role_gap" | "hero_pool_fit";

// SignalContribution gana el mismo campo opcional que el motor:
// applicable?: boolean;
```

**2. `apps/web/components/signal-breakdown/SignalBreakdown.tsx`**:
- `SIGNAL_LABELS` gana `hero_pool_fit: "Tu pool de héroes"` (o el texto equivalente que decidas,
  consistente con el resto — corto, en español, mismo tono que las otras 4).
- `SignalBreakdownRow` debe distinguir **tres** casos, no dos: `raw === null` (sin datos, fila ya
  existente `SignalBreakdownRowEmpty`), `applicable === false` (nueva fila, distinta de "sin
  datos" — mensaje explicando que la función no está configurada, no que falten datos), y el caso
  normal con `raw` numérico.
- Los tres textos de `hero_pool_fit` (ya definidos en el scorer, TSK-022, pero verificar que la UI
  los muestre tal cual, sin reescribirlos): "Configura tu pool de héroes para que las sugerencias
  tengan en cuenta con qué juegas cómodo" (no aplicable), "Fuera de tu pool de héroes" (candidato
  fuera), "En tu pool: X% en N partidas" (candidato dentro, con winrate).

## Reglas duras
- No cambiar el comportamiento de las 4 señales de fase 1 — sus filas se renderizan exactamente
  igual que antes.
- `applicable === false` **nunca** se muestra igual que `raw === null` — son mensajes distintos en
  la UI, igual que son casos distintos en el contrato (TSK-022/023). Confundirlos en la UI
  reintroduce el problema que `applicable` existe para evitar.
- Convenciones de `.claude/rules/web.md`: sin ternarios para renderizado condicional (usar early
  return o un componente propio, como ya hace `SignalBreakdownRow`/`SignalBreakdownRowEmpty`),
  tokens de diseño semánticos.

## Aceptación
- Una sugerencia con las 5 señales, `hero_pool_fit` con `applicable: false` → se ve una fila
  distinta a las de `raw: null` de otras señales, con el texto de "configura tu pool".
- Una sugerencia con `hero_pool_fit` aplicable y `raw` numérico → fila normal, con el texto
  correspondiente ("fuera de tu pool" o "en tu pool: X% en N partidas" según corresponda).
- Las 4 señales de fase 1 siguen renderizando exactamente igual que antes de este ticket
  (verificar contra `SuggestionCard`/pruebas existentes, sin regresión visual ni de datos).
