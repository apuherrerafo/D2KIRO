## Contexto/Problema

Depende de TSK-072. El turno actual (lado, acción esperada, tiempo base restante, reserva
restante) que el reductor ya calcula necesita llegar a `apps/web` — hoy `ServerMessage`
(`apps/engine/src/draft/types.ts` / espejado en `apps/web/features/draft/types.ts`) solo empuja
`draft_state` y `suggestions` (orden fijo, regla dura de `engine.md`: "draft_state antes que
suggestions"). Este campo se añade a `draft_state` en vez de abrir un tercer tipo de mensaje —
mismo criterio que ya se documentó para "caminos de draft" (Fase 2): un tercer push automático
solo se abre con una decisión explícita, y acá el turno es parte directa del estado del draft, no
un cálculo exploratorio bajo demanda como `draft-paths`.

Al reconectar (`hello`), el snapshot completo (regla dura, nunca deltas) debe incluir el turno
actual ya recalculado desde el estado persistido — nunca arrancar en cero como si el draft
empezara de nuevo.

## Alcance

- `DraftState.turn` (nuevo campo, tipo `DraftTurn | null` — `null` cuando no hay tabla de turnos
  aplicable, ver TSK-072): `{ side: TeamSide; action: "ban" | "pick"; baseRemainingMs: number;
  reserveRemainingMs: { radiant: number; dire: number } }`.
- Espejo a mano en `apps/web/features/draft/types.ts` (mismo patrón ya documentado ahí para
  `SignalId` — los dos procesos son independientes, sin import directo).
- `apps/engine/src/server/session.ts` (o el módulo que arme el snapshot/`draft_state` real —
  confirmar nombre exacto del archivo antes de implementar) pasa a incluir `turn` en cada push.

## Archivos impactados

  si difiere de `reducer.ts`)
- `apps/engine/src/server/session.ts` (nombre a confirmar)

## Criterios de aceptación

1. `draft_state` incluye `turn` con el shape exacto arriba; `suggestions` sigue empujándose
   después, sin cambios de orden.
2. Un `hello` post-reconexión devuelve un `snapshot` con `turn` ya recalculado desde el estado

## Resultado

Shape real (ajustada al diseño ya cerrado en TSK-072, más simple que el borrador original de este
ticket): `DraftTurn = { side: TeamSide; action: "ban" | "pick"; standardTimeMs: number }` --
`baseRemainingMs`/`reserveRemainingMs` NO viven dentro de `turn` porque `reserveRemainingMs` ya es
un campo de primer nivel de `DraftState` desde TSK-072 (no había motivo para duplicarlo anidado), y
`baseRemainingMs` lo deriva el cliente (`turnStartedAt` + `standardTimeMs`, TSK-074) en vez de que
el motor lo recalcule en cada push -- mismo criterio que `DraftTimer.tsx` ya usa para el simulador.

`turn` **nunca se guarda** en el `DraftState` persistido de `SessionStore` (decisión ya tomada en
TSK-072: evitar cachear una vista redundante) -- se calcula recién al armar el mensaje saliente.
Nuevo helper `withTurn(state)` en `apps/engine/src/server/app.ts` (no `session.ts`, que solo define
tipos/`buildServerMessage` -- el punto real de armado del mensaje es `app.ts`), usado en los dos
lugares que empujan `draft_state`/`snapshot`: `pushSessionUpdate` (tras cada evento aplicado) y la
rama `hello` del WebSocket. `AppDeps` gana `captainsModeTurns?` (mismo patrón inyectable que
`heroCapabilities`/`heroPositions`, costura S10 -- las pruebas nunca usan la tabla real de 24
turnos).

Espejo completo en `apps/web/features/draft/types.ts`: `DraftTurn` nuevo + los 4 campos que
`DraftState` ganó (`firstPickSide`, `turnStartedAt`, `reserveRemainingMs`, `turn`). Esto rompió la
construcción de tipos en 7 lugares de `apps/web` que arman un `DraftState` literal a mano
(fixtures de test + 2 archivos reales del Random Draft Simulator, que siempre son `format:
"all_pick"` -- los 4 campos nuevos quedan en `null` ahí, nunca tienen tabla de turnos que
aplicarles). Se corrigieron todos antes de cerrar. Nuevo `CAPTAINS_MODE_RESERVE_TIME_MS = 130000`
en `constants.tsx` (espejo del total de reserva, solo para dibujar la barra como porcentaje en
TSK-074 -- el wire manda cuánto queda, nunca el total).
