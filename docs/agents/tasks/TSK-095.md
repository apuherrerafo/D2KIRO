## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5, `docs/specs/SPEC.md` §12.7 (migración `0006`)
y §12.17 (ticket 2 de Bloque A). Depende de TSK-094 (`accounts` debe existir para la FK). Hoy
`hero_pool` tiene `heroId` como único PK (`schema.ts:63-71`) — un solo pool global para todo el
proceso. Este ticket lo convierte en un pool por cuenta, **sin conectar todavía ningún control de
acceso a las rutas** (eso es TSK-098) — el `accountId` entra como parámetro explícito de las
funciones de query/ruta, resuelto por quien las llame.

## Alcance — 3 archivos (excepción de migración de CLAUDE.md)

### 1. `apps/engine/src/db/schema.ts`
```ts
export const heroPool = sqliteTable(
  "hero_pool",
  {
    accountId: integer("account_id").notNull().references(() => accounts.steamAccountId),
    heroId: integer("hero_id").notNull().references(() => heroes.id),
    source: text("source").notNull().$type<"manual" | "calculated">(),
    personalWinrate: real("personal_winrate"),
    personalGames: integer("personal_games").notNull().default(0),
    updatedAt: text("updated_at").notNull(),
  },
  (table) => [primaryKey({ columns: [table.accountId, table.heroId] })],
);
```

### 2. `apps/engine/src/db/migrations/0006_hero_pool_account.sql` (nuevo) + `_journal.json`
SQLite no soporta `ALTER TABLE` para cambiar una PK — patrón tabla-nueva/copiar/drop/rename, DDL
exacto en SPEC.md §12.7:
```sql
CREATE TABLE `hero_pool_new` (
	`account_id` integer NOT NULL,
	`hero_id` integer NOT NULL,
	`source` text NOT NULL,
	`personal_winrate` real,
	`personal_games` integer DEFAULT 0 NOT NULL,
	`updated_at` text NOT NULL,
	PRIMARY KEY(`account_id`, `hero_id`),
	FOREIGN KEY (`account_id`) REFERENCES `accounts`(`steam_account_id`) ON UPDATE no action ON DELETE no action,
	FOREIGN KEY (`hero_id`) REFERENCES `heroes`(`id`) ON UPDATE no action ON DELETE no action
);
--> statement-breakpoint
INSERT INTO `hero_pool_new` (`account_id`, `hero_id`, `source`, `personal_winrate`, `personal_games`, `updated_at`)
SELECT (SELECT `steam_account_id` FROM `accounts` LIMIT 1),
       `hero_id`, `source`, `personal_winrate`, `personal_games`, `updated_at`
FROM `hero_pool`
WHERE (SELECT COUNT(*) FROM `accounts`) = 1;
--> statement-breakpoint
DROP TABLE `hero_pool`;
--> statement-breakpoint
ALTER TABLE `hero_pool_new` RENAME TO `hero_pool`;
```
`_journal.json` gana `idx: 6`. **Con 0 o ≥2 cuentas, las filas de `hero_pool` NO se copian** — no
se adivina el dueño (mismo criterio que 0/≥2 en TSK-094).

### 3. `apps/engine/src/db/queries.ts` + los llamadores en `apps/engine/src/server/routes/hero-pool.ts`
`getHeroPool(db)` → `getHeroPool(db, accountId)` con `WHERE account_id = ?`. `replaceHeroPool(db,
rows)` → `replaceHeroPool(db, accountId, rows)`, el `tx.delete` gana el mismo `WHERE`. Los 3
handlers de `hero-pool.ts` (`get`/`put`/`calculate`) pasan a recibir `accountId` como parámetro de
función — **todavía no lo leen de ningún token** (eso es TSK-098); por ahora el punto de llamada
en `app.ts` puede pasar un valor fijo/de prueba, documentado como temporal en un comentario que
TSK-098 elimina.

## Casos a probar (S8, extendido)
1. `replaceHeroPool` escribe solo en la cuenta indicada — una segunda cuenta con pool propio no se
   toca.
2. `getHeroPool(db, X)` nunca devuelve filas de la cuenta `Y`.
3. Migración `0006` con exactamente 1 cuenta real: todas las filas de `hero_pool` se le asignan,
   mismo conteo antes/después.
4. Migración `0006` con 0 cuentas: `hero_pool` queda vacía tras migrar (o mantiene sus filas viejas
   sin `account_id`, según cuál sea más seguro — decidir contra el `WHERE` de la migración, no
   inventar un tercer comportamiento).
