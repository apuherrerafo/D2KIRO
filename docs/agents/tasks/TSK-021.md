## Contexto (ticket autocontenido)
Proyecto: dota2coach. Este ticket conecta tres piezas que ya deben existir por separado:
`OpenDotaClient.getPlayerHeroes` (TSK-018), el cálculo puro del pool propuesto (TSK-019, S7), y la
validación de `accountId` (definida en TSK-018). Es el único endpoint de 1b que toca la red — por
eso es un ticket propio, separado de TSK-020 (que solo lee/escribe SQLite).

**Depende de TSK-018 y TSK-019 completos.** No depende de TSK-020 para funcionar (este endpoint
nunca escribe en `hero_pool` — solo propone), pero comparten el mismo router de `app.ts`.

**Nota de `@redteam` de TSK-018 (evt-20260729-007)**: `getPlayerHeroes` devuelve el array crudo sin
filtrar — `isValidRawPlayerHero`/`mapPlayerHero` (`apps/engine/src/meta/validation.ts`/`mappers.ts`)
son primitivas de una sola fila, no descartan nada por sí solas. Este ticket es quien debe iterar
el array de la respuesta, aplicar `isValidRawPlayerHero` como filtro y `mapPlayerHero` por cada fila
válida antes de pasarle el resultado a la función pura de TSK-019 — mismo patrón exacto que
`syncHeroes`/`syncPatchStats`/`syncMatchups` ya usan en `apps/engine/src/meta/sync.ts` para
`/heroStats` y `/heroes/{id}/matchups`. Un registro con forma inesperada se descarta, no rompe el
cálculo del pool.

## Contrato exacto (§9.5 de `docs/specs/SPEC.md`)

`POST /api/hero-pool/calculate`
`{ accountId: string, days?: number }` (default `days: 90`)
→ `200 { proposed: HeroPoolEntry[], baselineWinrate: number, consideredHeroes: number, windowDays: number }`

**No escribe en SQLite.** Solo propone — el `PUT /api/hero-pool` (TSK-020) es el único camino de
escritura, y lo dispara el usuario desde la UI (TSK-025) después de revisar la propuesta.

## Errores, explícitos (todos ya definidos en el SPEC, no hay margen de interpretación)

| Situación | Respuesta |
|---|---|
| `accountId` con formato inválido | `400 { error: 'invalid_account_id' }`. **Nunca se eco el valor recibido** en el cuerpo ni en ningún log. |
| OpenDota 429 o caído tras los 3 reintentos ya implementados en el cliente | `502 { error: 'opendota_unavailable' }` + mensaje en llano. El pool guardado (si existe) sigue intacto y las sugerencias del motor siguen funcionando — mismo principio que `stale_meta` en la sincronización de meta de fase 1. |
| Un `calculate` ya en curso (para la misma sesión/proceso) | `409 { error: 'calculation_in_progress' }`. Sin cola, sin reintento automático — el segundo request simplemente se rechaza. |
| Ningún héroe pasa el mínimo de partidas | `200` con `proposed: []`. **No es un error.** |

## Reglas duras
- **Nunca loguear ni ecoar `accountId`** en ningún error, response de log, `journal.md` o ticket —
  es el primer dato personal del proyecto. Un `accountId` filtrado en un mensaje de error es
  hallazgo de `@redteam`.
- Esta llamada de red **no toca el camino caliente del draft**: vive en el flujo de configuración,
  nunca se dispara durante una sesión de draft activa. La regla "cero red en el camino caliente"
  del motor de sugerencias sigue intacta — este endpoint es parte de `apps/engine` pero fuera del
  pipeline de `buildSuggestions`.
- Sin dependencias nuevas. Sin secreto nuevo (OpenDota no requiere API key para este endpoint).
- `apps/engine` sigue atado únicamente a `127.0.0.1`.

## Aceptación
- `accountId` con letras o fuera de rango → `400 invalid_account_id`, sin llegar a llamar a
  `OpenDotaClient`.
- Mock de `OpenDotaClient.getPlayerHeroes` que lanza tras agotar reintentos → `502
  opendota_unavailable`, mensaje en llano en el cuerpo.
- Dos requests simultáneos con el mismo `accountId` (o cualquiera, según cómo se implemente la
  detección de "en curso") → el segundo recibe `409 calculation_in_progress`.
- Mock que devuelve historial sin ningún héroe pasando el mínimo → `200 { proposed: [], ... }`.
- Caso feliz con fixture real de OpenDota (grabado, no red real en la prueba) → `200` con
  `proposed` de hasta 5 entradas, `baselineWinrate` y `consideredHeroes` coherentes con el fixture.
