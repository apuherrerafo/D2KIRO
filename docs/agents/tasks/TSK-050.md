## Contexto (ticket autocontenido)
Proyecto: dota2coach. `apps/engine` es un servidor Bun con SQLite + Drizzle ORM
(`apps/engine/src/db/schema.ts`, tablas existentes: `heroes`, `hero_patch_stats`, `hero_matchups`,
`meta_sync`, `settings`, `hero_pool`, `team_groups`, `team_members`).

Origen: sesión de QA manual de Fase 3 (2026-08-21). El usuario va a hacer sus propios drafts de
prueba y quiere poder escribir un reporte de texto libre ("esta sugerencia estuvo mal", "acá no
tiene sentido") directamente desde la pantalla de `/draft`, sin tener que copiar/pegar nada a
mano. Decisión acordada con el usuario: el reporte **nunca se guarda solo como texto suelto** --
siempre va acompañado de una foto exacta del estado del draft y de las sugerencias que se veían
en ese momento, para que se pueda diagnosticar después sin tener que adivinar el contexto.

Este es el primero de 3 tickets encadenados (mismo patrón que hero_pool en fase 1b): **050**
(esta migración) → **051** (los 2 endpoints que la usan) → **052** (la caja de texto en
`apps/web`). Excepción de simplicidad documentada por adelantado: schema + migración cuentan como
una sola unidad lógica aunque el snapshot autogenerado de `drizzle-kit` infle el conteo de líneas.

## Esquema exacto a implementar (Drizzle, SQLite)

Tabla nueva `draft_feedback`:

| Columna | Tipo | Nota |
|---|---|---|
| `id` | integer PK autoincrement | |
| `session_id` | text, not null | La sesión de draft a la que pertenece el reporte |
| `comment` | text, not null | El texto libre del usuario |
| `draft_state` | text JSON, not null | `DraftState` completo tal cual llegó del store en ese instante -- picks, bans, format, localSide, todo |
| `suggestions` | text JSON, nullable | `SuggestionSet` completo (las 3 sugerencias + señales + reason + comparison) en ese instante -- `null` solo si el reporte se manda antes de que llegara ninguna sugerencia |
| `created_at` | text ISO-8601, not null | |

**No se crea ningún endpoint de borrado ni de edición en este ticket** -- es un inbox append-only,
mismo espíritu que `journal.md`. Si algún día hace falta borrar un reporte ya revisado, es un
ticket aparte, explícito.

## Reglas duras
- Toda columna/query vía Drizzle. Cero SQL concatenado.
- Migración generada con el CLI de Drizzle (`npx drizzle-kit generate`), no escrita a mano.
- Sin dependencias nuevas.
- `draft_state`/`suggestions` se guardan como JSON crudo (`{ mode: "json" }`, sin tipar el shape
  exacto con `$type<...>()` -- a diferencia de otras columnas JSON de este archivo, acá el tipo
  real vive en `apps/web` y cambia con cada fase; forzar un `$type` en el motor lo acoplaría a un
  contrato que no es su responsabilidad mantener sincronizado).

## Fuera de alcance
- Los endpoints que escriben/leen esta tabla (TSK-051).
- La caja de texto en `apps/web` (TSK-052).
- Cualquier validación de contenido del reporte (longitud máxima, etc.) -- vive en TSK-051, la
  capa de escritura, no en el esquema.

## Aceptación
- La migración crea `draft_feedback` con las 5 columnas y tipos exactos de la tabla de arriba.
- Una query de ejemplo (insert + select) contra `draft_feedback` funciona parametrizada vía
  Drizzle, incluida una columna JSON con un objeto anidado real (no un string plano).
- `bun test` sin regresiones, `tsc --noEmit` limpio.
