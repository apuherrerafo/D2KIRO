## Contexto (ticket autocontenido)
Proyecto: dota2coach. `apps/engine/src/server/app.ts` ya expone endpoints HTTP (incluidos
`GET`/`PUT /api/settings`, que sirven de precedente directo de patrón para este ticket). Este
ticket agrega los dos endpoints de lectura/escritura del hero pool. Depende de TSK-017 (la tabla
`hero_pool` debe existir).

**No depende de TSK-018/019** (el cálculo automático) — este ticket es solo leer/escribir el pool
ya guardado, sea manual o ya calculado. `POST /api/hero-pool/calculate` es un ticket aparte
(TSK-021) porque involucra red hacia OpenDota; estos dos endpoints nunca tocan la red.

## Contrato exacto (§9.5 de `docs/specs/SPEC.md`)

| Método | Ruta | Cuerpo / respuesta |
|---|---|---|
| `GET` | `/api/hero-pool` | → `200 HeroPoolEntry[]` |
| `PUT` | `/api/hero-pool` | `{ entries: HeroPoolEntry[], baselineWinrate?: number \| null }` → `200 HeroPoolEntry[]`. **Reemplaza el pool completo, en una sola transacción.** Único camino de escritura — no hay `POST`/`DELETE` de una sola entrada. |

```ts
interface HeroPoolEntry {
  hero: number; // HeroId
  source: 'manual' | 'calculated';
  personalWinrate: number | null;
  personalGames: number;
  updatedAt: string;
}
```

## Validaciones del `PUT` (todas en el borde, antes de tocar la base)

| Situación | Respuesta |
|---|---|
| `entries` con más de 5 elementos | `400` con el motivo. El pool guardado **no se toca**. |
| `heroId` duplicado dentro de `entries` | `400`. Igual: no se toca lo guardado. |
| `heroId` que no existe en la tabla `heroes` | `400`. Un héroe inventado nunca entra al pool. |
| `personalWinrate` fuera de `[0,1]` (y no `null`) | `400`. |
| `personalGames` negativo o no entero | `400`. |

Todas estas validaciones se resuelven **antes** de abrir la transacción de escritura — si algo
falla, la tabla `hero_pool` queda exactamente como estaba.

## Reglas duras
- Toda query vía Drizzle. Cero SQL concatenado.
- El `PUT` es una transacción real: borrar todo + insertar las nuevas entradas dentro de la misma
  transacción de Drizzle. Un fallo a mitad de camino nunca deja el pool a medio reemplazar — mismo
  principio que la sincronización de meta (S6) de fase 1.
- Ambos endpoints en el régimen "páginas normales" (sin `x-capture-token`, CORS ya habilitado para
  `apps/web` desde TSK-013/014 — revisar cómo está configurado CORS en `app.ts` antes de repetir
  ese trabajo).
- `apps/engine` sigue atado únicamente a `127.0.0.1` — no toques el binding.
- **No expandir el alcance**: nada de lógica de cálculo automático aquí (eso es TSK-021), nada de
  UI (eso es TSK-024).

## Aceptación
- `GET` con el pool vacío (nunca configurado) → `200 []`, no un error.
- `PUT` con 3 entradas válidas → `200` con esas 3 entradas; `GET` posterior las refleja.
- `PUT` con 6 entradas → `400`, y un `GET` posterior confirma que el pool anterior sigue intacto
  (o vacío, si nunca se había configurado).
- `PUT` con un `heroId` repetido dentro del mismo body → `400`, pool sin cambios.
- `PUT` con un `heroId` que no existe en `heroes` → `400`, pool sin cambios.
- Prueba de integración: simular un fallo a mitad de la transacción (ej. mock de Drizzle que lanza
  en el segundo insert) y confirmar que el pool queda como antes del intento, no a medias.
