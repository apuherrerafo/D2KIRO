3 páginas (`app/{meta,heroes,settings}/page.tsx`) + fix del gap de `settings` en `apps/engine`

**Bugs reales encontrados y corregidos en el camino, fuera del alcance original del ticket:**
- `apps/engine/src/db/migrate.ts` tenía el mismo bug que TSK-010 ya había corregido en
  `db/client.ts` (directorio `data/` faltante) pero en un archivo separado que no reutilizaba el
  fix — `bun run db:migrate` fallaba en un checkout limpio. Corregido reutilizando `db/client.ts`.

  `react-hooks/refs` en la versión de `eslint-plugin-react-hooks` de este proyecto — corregido con
  `useState(() => makeStore())`, el patrón correcto para esta versión (AGENTS.md ya advertía sobre
  breaking changes de esta versión de Next.js).

**Notas abiertas:**

  el binding a `127.0.0.1` ya es el perímetro de seguridad real; esto solo destraba la llamada
  cross-port legítima de `apps/web`, nunca un origin remoto.
- No se probaron los componentes de página con una librería de renderizado de React (mismo criterio
  que TSK-012/013: evita otra dependencia nueva) — verificado con smoke tests reales contra el
  servidor vivo en su lugar.

## Contexto (ticket autocontenido)
Proyecto: dota2coach — sitio web con visión futura de cuentas/login (no en fase 1). Depende de
TSK-001 (esqueleto `apps/web`) y TSK-010 (`GET /api/heroes`, `GET /api/meta/status`,
`POST /api/meta/sync`). No es parte de los 4 criterios de aceptación de fase 1 (captura,
sugerencias, velocidad, simulador) — es soporte al producto, de ahí `moscow: should`, no `must`.

## Qué construir
- Páginas normales del sitio (no la vista de draft en vivo — esa es TSK-012 y usa
  WebSocket/Zustand, nunca RTK Query):
  - **Estado del meta**: muestra `syncedAt`/`isStale` de `GET /api/meta/status`, botón para
    disparar `POST /api/meta/sync` manualmente.
  - **Héroes**: lista desde `GET /api/heroes`, cada héroe con su `img_url` oficial (validando el
    host contra la lista permitida del CDN de Valve antes de renderizar).
  - **Configuración**: página simple sobre `settings` (ver esquema de TSK-002) — sin
    implementar autenticación, solo preferencias locales de fase 1.
- Todas estas páginas usan RTK Query contra `apps/engine` — es el régimen de datos por defecto
  del sitio (la excepción WebSocket/Zustand es solo para la vista de draft).

## Reglas duras (mismas de `.claude/rules/web.md`)
- TypeScript estricto sin `any`, sin ternarios para renderizado condicional, sin funciones
  anónimas, arquitectura por features.
- Prohibido `dangerouslySetInnerHTML`.
- Tokens de diseño semánticos (`--surface-*`, `--content-*`, etc.), nunca un hex suelto.
- Estructura de rutas preparada para añadir login más adelante sin reescritura — no se
  implementa nada de auth aquí, solo se evita bloquear esa puerta.

## Aceptación
- Las 3 páginas cargan datos reales vía RTK Query contra los endpoints de `apps/engine`.
- Disparar la sincronización manual desde la página de estado del meta invoca
  `POST /api/meta/sync` y refleja el nuevo `syncedAt` al terminar.
- Cada héroe en la lista muestra su ícono oficial, sin excepción.
