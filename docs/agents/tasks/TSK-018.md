## Contexto (ticket autocontenido)
Proyecto: dota2coach. `apps/engine/src/meta/opendota-client.ts` ya existe con `getHeroes`,
`getMatchups`, `getHeroStats` — todos devuelven `unknown` a propósito (la validación vive en el
borde, nunca en el cliente) y comparten `fetchWithRetry` (reintentos 1s/4s/16s en 429 o caída de
red, ya implementado, no lo reimplementes). Este ticket agrega un cuarto método al mismo patrón de
clase, para poder "calcular el pool desde mis partidas" (fase 1b).

## Método nuevo

```ts
getPlayerHeroes(accountId: string, options?: { days?: number }): Promise<unknown>
// GET /players/{account_id}/heroes?date={days}
```

- Mismo patrón que los tres métodos existentes: usa `getJson`/`fetchWithRetry` ya implementados,
  devuelve `unknown`.
- `days` por defecto: **90**. El nombre exacto del parámetro de fecha en la API real de OpenDota
  (se documenta como `date`, en días) se confirma contra el Swagger en vivo antes de cerrar este
  ticket — si difiere, es un cambio de una línea en la URL, no un rediseño.
- No valida `accountId` aquí — ver siguiente sección, la validación es una responsabilidad
  separada y va antes de que este método se llame, no dentro de él.

## Validación en el borde (nuevo, no existía en fase 1: primer dato personal del proyecto)

Función pura de validación de `accountId` (Steam32), en un archivo propio o junto a
`apps/engine/src/meta/validation.ts` (ya existe para las respuestas de OpenDota — revisar el
patrón antes de decidir dónde va):
- Válido: **solo dígitos decimales**, valor entre `1` y `4294967295`.
- Un `accountId` que no pase la validación **nunca** debe llegar a construir una URL ni a
  `fetch` — se rechaza antes.
- Esta función se usa desde el endpoint HTTP (TSK-021), pero se define y se prueba aquí, aislada.

## Validación de la respuesta (mismo patrón que `mappers.ts`/`validation.ts` ya existentes)

La respuesta de `/players/{account_id}/heroes` es un array de objetos con (según la doc pública de
OpenDota) al menos `hero_id`, `games`, `win`. Escribe el mapeo/validación que extrae solo estos
campos y descarta filas con forma inesperada — igual que ya se hace para `/heroStats` y
`/heroes/{id}/matchups`. Un registro inválido se descarta, no rompe el resto.

## Reglas duras
- Cero red en las pruebas: usa `fetchImpl` inyectable (ya soportado por `OpenDotaClientOptions`)
  con respuestas grabadas en fixtures.
- Sin dependencias nuevas.
- **Nunca loguear ni ecoar el `accountId`** en errores, journal.md o tickets — es el primer dato
  personal del proyecto (vincula a una cuenta real de Steam). Trátalo con el mismo cuidado que
  cualquier credencial, aunque técnicamente sea un endpoint público sin autenticación.

## Aceptación
- `getPlayerHeroes('123', { days: 90 })` contra un `fetchImpl` fake que devuelve un payload
  grabado real → array de objetos mapeados con `hero_id`/`games`/`win`.
- Validación de `accountId`: casos válidos (dígitos, dentro de rango) y casos inválidos (letras,
  vacío, `0`, mayor a `4294967295`, con espacios) — todos los inválidos rechazados antes de tocar
  `fetch`.
- Un 429 de OpenDota en este endpoint respeta el mismo backoff ya probado en los otros tres
  métodos (reutiliza `fetchWithRetry`, no lo reescribe).
