## Fórmula exacta

Para un candidato `c` y el conjunto de héroes baneados `B = state.banned`:

```
BanAwareRaw(c) = Σ_{b∈B}  calculateDenialScore(c, target(b), banRelief, commitment, BETA_OPENING)

donde calculateDenialScore(c, target(b), …) =
    Σ_{p=1..5} P(Pos_b = p) · banRelief(c, b, p)
  + BETA_OPENING · commitment(c) · H(b)
```

| Símbolo | Definición exacta | Origen |
|---|---|---|
| `target(b)` | `inferFlexPick(b, heroPositions, DEFAULT_ENTROPY_THRESHOLD)` | `intent/flex-inference.ts`, sin cambios |
| `P(Pos_b=p)` | `target(b).distribution.probabilities[p]` | `intent/position-prior.ts`, sin cambios. Sin dato → uniforme `0.2` |
| `H(b)` | `target(b).distribution.entropy`, bits, `[0, log₂5≈2.3219]` | ídem |
| `banRelief(c,b,p)` | ver abajo | nuevo |
| `commitment(c)` | `1 − H(c)/log₂5`, en `[0,1]` | nuevo, sobre `deriveFlexDistribution(c, heroPositions)` |
| `BETA_OPENING` | **`0.04`** | nuevo — medido: con el `DEFAULT_BETA=0.5` por defecto la entropía dominaría ~12:1 sobre el matchup |

## Alcance — 2 archivos

**Nuevo** `apps/engine/src/pipeline/ban-relief.ts`:

```ts
import { deriveFlexDistribution } from "../intent/position-prior";
import { MIN_MATCHUP_GAMES, type MatchupWinrateFn } from "./meta-matchup";
import type { HeroId } from "../draft/reducer";
import type { HeroPositions } from "../signals/hero-positions";
import type { HeroMatchupStat } from "../signals/types";

// 1 / UNIFORM_PROBABILITY de intent/position-prior.ts. Un candidato sin dato de posición cae en
// la uniforme (0.2 en las cinco) y este factor lo devuelve exactamente a 1.0 -- el alivio plano
// de team-opener.ts, ni más ni menos. Un hueco de datos nunca penaliza.
export const POSITION_OVERLAP_GAIN = 5;

export const BETA_OPENING = 0.04;

export function createBanReliefWinrate(
  matchups: Record<HeroId, HeroMatchupStat[]>,
  heroPositions: HeroPositions,
): MatchupWinrateFn;

export function createPositionalCommitment(
  heroPositions: HeroPositions,
): (heroId: HeroId) => number;
```

`banRelief(c, b, p)`, exactamente:
1. `row = matchups[c]?.find(m => m.vsHero === b)` — vía el índice de `meta-matchup.ts` (TSK-128).
2. `row` ausente o `row.games < MIN_MATCHUP_GAMES(200)` → `null` (posición saltada de la suma).
3. `relief = Math.max(0, 0.5 - row.wins/row.games)` — idéntico al primitivo de `reliefScore` en
   `team-opener.ts`. Matchup favorable → `0`, nunca negativo.
4. `return POSITION_OVERLAP_GAIN * P(Pos_c = p) * relief`.

`createPositionalCommitment(c)`: `1 - deriveFlexDistribution(c, heroPositions).entropy / Math.log2(5)`.
Rango cerrado `[0,1]`, memoizado en un `Map<HeroId, number>` por corrida.

## Criterios de aceptación

- **Prueba del ancla (obligatoria, no opcional)**: un candidato **sin dato de posición** produce
  exactamente el mismo alivio que el mecanismo plano actual — `POSITION_OVERLAP_GAIN` existe
  precisamente para garantizar esto.
- Sin bans (`B` vacío) → el término es `raw: null`, nunca `0` (verificar en el ticket que conecta
  esto a `run-pipeline.ts`, pero el contrato de esta función ya debe soportarlo).
- Un ban que no comparte posición con el candidato (`overlap ≈ 0`) aporta relief ≈ 0, aunque el
  matchup sea muy favorable — el solapamiento posicional es un factor multiplicativo, no aditivo.
- `commitment(c)` nunca es negativo ni mayor a 1 — la entropía de Shannon sobre 5 símbolos está
  acotada por `log₂5` por definición, no hace falta `clamp`.
