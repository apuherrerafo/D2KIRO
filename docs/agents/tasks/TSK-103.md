## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5, `docs/specs/SPEC.md` §12.9, §12.15-B y
§12.17 (ticket 10 de Bloque B). Depende de TSK-102 (`lib/account-token.ts`, acuñado) y TSK-099
(`apps/engine` ya espera `accountToken` en el `hello`). **Corrección real de `/blueprint`
(SPEC.md §12.15-B)**: la cookie de sesión no puede viajar en el `hello` del WebSocket — no es solo
que no sea confiable entre orígenes distintos (lo que ya descartaba el diseño original), es que el
navegador tampoco puede firmar el token él mismo. Por eso existe este endpoint dedicado, que acuña
del lado del servidor.

## Alcance — 3 archivos

### 1. `apps/web/app/api/auth/engine-token/route.ts` (nuevo)
`GET`, exige sesión (`iron-session`). Devuelve `{ token: string, expiresAt: number }` — el token es
el mismo `x-account-token` de `lib/account-token.ts` (TSK-102), vive 60 s y es de un solo uso (mismo
contrato exacto que el camino HTTP, no uno paralelo).

### 2. `apps/web/features/draft/socket.ts`
`createDraftSocket` (o la función real de conexión) pide el token vía este endpoint
**inmediatamente antes de cada conexión, incluida cada reconexión** — nunca lo guarda en
`localStorage` ni lo reutiliza entre intentos. El mensaje `hello` (`store.ts`) gana `accountToken`
junto a `sessionId`.

### 3. `apps/web/features/random-draft-simulator/use-random-draft-session.ts` (o el hook real que
abre WebSocket para el simulador, si corresponde al mismo mecanismo — verificar contra el código
real si el simulador comparte el mismo `hello`/socket que `DraftView` antes de asumirlo)
Mismo patrón: pedir el token antes de cada conexión/reconexión.

## Casos a probar
1. `GET /api/auth/engine-token` sin sesión → `401`.
2. Con sesión válida → `{ token, expiresAt }`, y ese `token` es aceptado por `verifyAccountToken`
   (`apps/engine`, TSK-097/TSK-099).
3. El cliente pide un token nuevo en cada intento de conexión — dos conexiones seguidas usan dos
   tokens distintos, nunca el mismo reutilizado (verificar con un spy sobre el fetch del endpoint).
4. Reconexión tras un corte: el cliente pide un token nuevo antes de reconectar, no reintenta con
   el viejo (que ya venció o ya se consumió).
5. Un token expirado/ya usado que el cliente intentara reenviar es rechazado por `apps/engine`
   (TSK-099) — este ticket verifica que el cliente nunca llega a intentarlo, no que el servidor lo
   rechace (eso ya lo cubre TSK-099).
