## Contexto

El draft en vivo hoy sólo funciona en la máquina del desarrollador: Dota → `127.0.0.1` → motor
local (Overwolf o `bun run probe:gsi`). En Railway `/live-draft` muestra "no disponible". El usuario
quiere abrir la URL de staging, iniciar sesión con Steam, apretar **Conectar Dota**, instalar un
archivo una vez, reiniciar Dota y ver el Team Coach Board alimentado por Dota.

## Frontera de confianza nueva (gatillo documentado de CLAUDE.md)

`POST /api/live/gsi/<liveId>` es **público** (Dota no tiene cookie de sesión). Mitigación
obligatoria — ninguna opcional:

- `liveId` opaco (256 bits) + token por enlace (256 bits) en el bloque `auth` del `.cfg`. El motor
  guarda **sólo el hash SHA-256** del token; comparación en tiempo constante.
- Enlace = cuenta autenticada (sesión de Steam, server-side). La identidad **nunca** sale del cuerpo
  GSI (`player.steamid`/`accountid`/`name` se ignoran por allowlist).
- Vencimiento (30 días), rotación (descargar de nuevo revoca el anterior), revocación explícita.
- Cuerpo acotado (relay de `apps/web` y motor), JSON malformado → 400, límite por enlace y límite
  global de fallos de autenticación → 429. Falla cerrado.
- Nunca se registra el payload, el token, Steam IDs, nombres ni match id (sólo su hash en memoria).
- `apps/engine` sigue atado a `127.0.0.1`: el único camino público es un relay de una sola ruta en
  `apps/web`.
- El `.cfg` se genera sólo con origen `https:` (`PUBLIC_BASE_URL`), por POST same-origin.

## Alcance

1. Motor: `live/gsi-normalize.ts` (puro), `live/gsi-links.ts` (Drizzle, migración `0009`),
   ruta de ingesta + rutas de enlace, `LiveCaptureRegistry.ingestGsi` sobre el kernel existente

2. Web: relay público, descarga del `.cfg`, flujo "Conectar Dota" en `/live-draft`, copy sin
   herramientas de desarrollador, link "Draft en vivo" en el nav.
3. Herramientas de desarrollador (`dev:live`, `probe:gsi`, Overwolf) se conservan como diagnóstico.

## Criterios de aceptación

- Pruebas: creación, propiedad, token inválido/vencido/revocado, malformado, sobredimensionado,
  límite de tasa, idempotencia, reconexión, normalización, bando, capacidades de draft, cero log de
  payload/identidad/token, aislamiento entre cuentas, fallback manual, recálculo del Team Coach.
- `bun run test`, `tsc` de ambos procesos, lint de `apps/web`, `verify-simplicity.sh` en verde.
- `@redteam` APPROVED y `/castoff` antes del deploy a staging. Producción y `master` intactos.

## Lo que sólo un cliente real de Dota puede confirmar (no se asume)

Todo lo demás se prueba con payloads GSI sintéticos (identidades centinela, nunca reales) y contra
staging. Pendiente de la primera partida real de Ranked All Pick:

1. Que el cliente de Dota acepte un `uri` **https** remoto (Railway) y POSTee ahí. Si no lo hace, la
   página queda en "Esperando Dota..." y el plan B es un companion de Windows sin terminal (no
   construido en este ticket).
2. Qué expone GSI a un **jugador** (no espectador) durante Hero Selection: el bloque `draft` puede
   llegar vacío. En ese caso la UI dice "Captura no disponible — usar entrada manual" y muestra qué
   informó Dota (bando / tu héroe / bans / picks). Nada se inventa.
3. Que `hero.id` aparezca recién al **lockear** el pick (no al hacer hover).
4. Qué campos de telemetría de partida llegan de verdad (`status.gsi.telemetry`, sólo presencia).
