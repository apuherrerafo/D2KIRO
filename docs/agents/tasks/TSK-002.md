## Contexto (ticket autocontenido — Codex no lee journal.md ni architecture.md)
Proyecto: dota2coach, motor de sugerencias de picks/bans para Dota 2. `apps/engine` es un
servidor Bun con SQLite + Drizzle ORM. Este ticket es la excepción documentada de
`CLAUDE.md`: schema + migración + 1 query afectada cuentan como **una sola unidad lógica**,
aunque toquen más de 1 archivo.

Depende de TSK-001 (esqueleto de `apps/engine` ya debe existir).

## Esquema exacto a implementar (Drizzle, SQLite)

| Tabla | Columnas | Nota |
|---|---|---|
| `heroes` | `id` PK, `name`, `localized_name`, `img_url`, `primary_attr`, `attack_type`, `roles` (JSON), `updated_at` | `img_url` cubre el requisito duro de mostrar siempre el ícono oficial |
| `hero_patch_stats` | `hero_id`, `patch`, `bracket`, `picks`, `wins`, `updated_at` — PK compuesta (`hero_id`, `patch`, `bracket`) | Alimenta la señal `patch_meta` |
| `hero_matchups` | `hero_id`, `vs_hero_id`, `games`, `wins`, `updated_at` — PK compuesta (`hero_id`, `vs_hero_id`) | Alimenta la señal `counter` |
| `meta_sync` | `id`, `source`, `started_at`, `finished_at`, `status`, `rows_written`, `error` | Auditoría de sincronización |
| `settings` | `key` PK, `value` | Preferencias locales |

**No crear tabla de historial de partidas** — es fase 1b, fuera de alcance.

## Contrato que consume este esquema (para que las columnas encajen)
```ts
interface MetaProvider {
  getHeroes(): Promise<HeroMeta[]>;
  getMatchups(hero: HeroId): Promise<MatchupRow[]>;
  getPatchStats(patch: string): Promise<PatchStatRow[]>;
  getFreshness(): Promise<{ syncedAt: string | null; isStale: boolean }>;
}
```
`SqliteMetaProvider` es la única implementación que usará el motor (ticket separado). Aquí solo
se define el esquema y las migraciones — no se implementa el provider todavía.

## Reglas duras

- Sin dependencias nuevas fuera de Drizzle/driver de SQLite ya decidido — si hace falta algo más,
  no lo añadas, repórtalo.
