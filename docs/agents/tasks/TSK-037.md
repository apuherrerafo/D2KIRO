Proyecto: dota2coach. Origen: decisión de arquitectura de deploy a Railway (2026-08-01, única

toca. Lo que cambia es que `apps/web` deja de conocerle la URL directa al navegador.

## Por qué (no inventar otra solución)
Hoy el navegador (RTK Query en `apps/web/lib/engine-api.ts`, y los fetch directos de
`use-hero-catalog.ts`/`manual-entry.ts`) llama directo a `NEXT_PUBLIC_ENGINE_HTTP_URL` -- una
variable horneada en el bundle del cliente. En Railway eso rompería (el navegador del usuario
nunca puede alcanzar el contenedor). La solución NO es exponer el engine a la red -- es que el
navegador le hable a su propio origen (`apps/web`), y que Next.js reenvíe internamente por
`127.0.0.1` vía `rewrites()`. Se evaluó y se descartó explícitamente la opción de dos servicios +
networking privado de Railway (el consumidor real es el navegador, no el servidor -- igual habría
que construir este mismo proxy, más un servicio extra).

## Cambios exactos
1. `apps/web/lib/engine-url.ts` (nuevo): único lugar que exporta la base URL relativa que el
   navegador debe usar (`/engine` por defecto, o el valor que se decida).
2. `apps/web/next.config.ts`: `async rewrites()` con **allowlist explícita de rutas, nunca
   `/:path*` comodín**. Lista completa y final (verificada contra las rutas reales de
   `apps/engine/src/server/app.ts` -- hallazgo de revisión de Codex, la lista original decía
   "etc." y quedaba incompleta):
   - `GET /engine/api/heroes`
   - `GET /engine/api/meta/status`, `POST /engine/api/meta/sync`
   - `GET /engine/api/settings`, `PUT /engine/api/settings`
   - `GET /engine/api/hero-pool`, `PUT /engine/api/hero-pool`, `POST /engine/api/hero-pool/calculate`
   - `GET /engine/api/team-groups`, `POST /engine/api/team-groups`
   - `GET /engine/api/team-groups/:id`, `PUT /engine/api/team-groups/:id`, `DELETE /engine/api/team-groups/:id`

   El destino de cada rewrite sale de una variable de SERVIDOR nueva `ENGINE_INTERNAL_URL`
   (**sin** prefijo `NEXT_PUBLIC_`, nunca llega al bundle del cliente).
   **`/engine/ingest/draft-event`, `/engine/api/session/manual` y
   `/engine/api/session/:id/draft-paths` NUNCA se listan** -- las dos primeras son las rutas de
   escritura sin autenticación fuerte del motor (ver TSK-038); la tercera solo tiene sentido con
   un draft activo, que no existe en el deploy cloud (TSK-038 la deja fuera también).
3. `apps/web/lib/engine-api.ts`, `apps/web/features/draft/use-hero-catalog.ts`,
   `apps/web/features/draft/manual-entry.ts`: dejan de leer `process.env.NEXT_PUBLIC_ENGINE_HTTP_URL`,
   toman la base de `engine-url.ts`.

Son 5 archivos -- excede el límite de 3. Partir en dos unidades lógicas si hace falta: A1 (crear
`engine-url.ts` + `next.config.ts`) y A2 (migrar los 3 consumidores), o pedir
`simplicity_exception: true` documentada aquí antes de empezar (hay precedente: 5 tickets de fase
1b lo usaron).

## Fuera de alcance
- `NEXT_PUBLIC_ENGINE_WS_URL` (`DraftView.tsx`) **no se toca** -- el WebSocket del draft en vivo
  solo existe en local, nunca se proxea (ver TSK-038).
- Cualquier cambio a `apps/engine/src/index.ts` o al binding de `127.0.0.1` -- cero cambios ahí.
- `ALLOWED_ORIGIN_PATTERN`/CORS en `app.ts` -- el tráfico proxeado es servidor-a-servidor, sin
  header `origin`, CORS deja de ser relevante en el cloud, no hace falta tocarlo.

## Aceptación
- En desarrollo local, todo sigue funcionando exactamente igual (el dev server de Next proxea a
  `127.0.0.1:4000`) -- regresión cero, verificable con la suite de pruebas existente sin cambios.
- Ninguna ruta de escritura sin autenticación (`/ingest/draft-event`, `/api/session/manual`)
  aparece en la lista de `rewrites()`.
- **Prueba negativa obligatoria** (hallazgo de revisión de Codex, guardrail contra un cambio
  futuro descuidado): un test dedicado confirma que `/engine/ingest/draft-event` y
  `/engine/api/session/manual` nunca responden vía `apps/web`, ni aunque alguien agregue después
  un rewrite más amplio "para que el draft funcione" -- el test debe fallar si eso pasa, no
  confiar solo en que el código de hoy es correcto.
- `NEXT_PUBLIC_ENGINE_HTTP_URL` desaparece del código -- ya no queda ningún lugar que la lea.
