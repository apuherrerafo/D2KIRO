## Los 6 estados — todos deben existir en pantalla, ninguno opcional
| Estado | Qué ve el usuario |
|---|---|
| `desconectado` | Aviso + botón de reconectar. El último estado conocido sigue visible, atenuado. |
| `esperando_draft` | "Esperando a que empiece el draft" + botón de entrada manual + botón de simulador. |
| `activo` | Tablero de picks/bans con íconos oficiales + 1 sugerencia principal + 2 alternativas + señales expandibles. |
| `degradado` | Igual que `activo`, con la bandera de degradación visible y explicada en lenguaje llano. |
| `completo` | Draft final, sin sugerencias nuevas. |
| `error` | Mensaje concreto + acción de recuperación. Nunca una pantalla en blanco. |

## Reglas duras
- Esta vista es la **única excepción** de datos en `apps/web`: WebSocket + Zustand, nunca RTK
  Query para el estado de draft en vivo.
- Al abrir el socket, el cliente manda `hello`; siempre espera un `snapshot` completo del
  servidor (no deltas) — ver `.claude/rules/engine.md`/TSK-010.
- Cada héroe se muestra siempre con su ícono/foto oficial (`img_url`), validando que el host esté
  en la lista permitida (CDN de Valve) antes de renderizar.
- Una sugerencia de `confidence: 'baja'` se muestra igual, marcada como tal — nunca se oculta.
- Convenciones de `.claude/rules/web.md`: sin `any`, sin ternarios para renderizado condicional,
  sin funciones anónimas, arquitectura por features, tokens de diseño semánticos (nunca un hex
  suelto).
- Nombres de componente `<Dominio><Cosa>`: `DraftBoard`, `DraftHeroSlot`, `SuggestionCard`,
  `SignalBreakdown`.

## Aceptación
- Los 6 estados son alcanzables y visualmente distintos, verificado manualmente o con el
  simulador de TSK-011.
- El mismo componente de vista sirve tanto en pestaña normal de navegador como preparado para
  embeberse en un overlay de Overwolf (sin lógica condicional de "modo overlay" bifurcando la UI).
- `SignalBreakdown` muestra las 4 señales de cada sugerencia, incluidas las que dieron `null`.
