## Alcance — 2 archivos

### 1. `apps/engine/src/server/account-token.ts` (nuevo)
Contrato exacto (SPEC.md §12.6, **copiar el vector de prueba tal cual, no recalcularlo**):
- Payload: `{accountId}.{issuedAtMs}.{nonce}.{firmaHMAC}`.
- Firma: HMAC-SHA256 sobre `"d2k-account-token/v1|" + accountId + "." + issuedAtMs + "." + nonce`,
  con `INTERNAL_AUTH_SECRET` (`process.env`, nunca literal ni default).
- Verificación, **en este orden exacto**: (1) forma del header (4 segmentos, tipos correctos) →
  (2) firma, comparación en **tiempo constante** (`crypto.timingSafeEqual` o equivalente) → (3)
  ventana: `issuedAtMs` dentro de 60 s + 5 s de tolerancia de reloj → (4) `accountId` es un Steam32
  válido (reusar `isValidSteamAccountId`) → (5) nonce no usado antes.
- Store de nonces: en memoria, ≤ ~1200 entradas en régimen normal, barrido oportunista a partir de
  5000 (mismo patrón que `SessionStore.evictStale`) — **inyectado**, no un singleton de módulo
  oculto, para que la prueba controle el reloj y el store (costura S13).
- Firma de la función principal:
  ```ts
  export function verifyAccountToken(
    header: string | undefined,
    secret: string,
    now: () => number,
    nonceStore: NonceStore,
  ): { ok: true; accountId: AccountId } | { ok: false; error: AccountTokenError };

  export type AccountTokenError =
    | "missing_account_token" | "invalid_account_token"
    | "expired_account_token" | "replayed_account_token";
  ```
  (`unknown_account` **no** se resuelve acá — ese error depende de si la cuenta existe en `accounts`,
  responsabilidad de quien llame a `verifyAccountToken`, ver TSK-098).

## Casos a probar (S13, reloj y nonce inyectados — nunca `Date.now()`/store real)
1. Vector de prueba de §12.6 produce la firma exacta esperada — candado compartido con `apps/web`
   (TSK-100/TSK-102 deben producir la misma firma para el mismo input).
2. Header ausente → `missing_account_token`.
3. Firma alterada (1 bit distinto) → `invalid_account_token`, nunca se llega a validar la ventana.
4. Dentro de la ventana (< 60 s) → válido.
5. **Fuera de la ventana** (> 65 s con la tolerancia) → `expired_account_token`.
6. **Nonce reenviado dentro de la ventana** (mismo token, dos veces) → la segunda vez,
   `replayed_account_token`. **Es una prueba distinta de la 5** — un solo test de "vencido" no
   detecta un anti-replay inexistente (mismo tipo de hallazgo que TSK-036).
7. `accountId` fuera del rango Steam32 (`0`, negativo, `> 4294967295`) → `invalid_account_token`.
8. Orden de verificación: una firma inválida con `accountId` también inválido devuelve
   `invalid_account_token` por la firma, nunca llega a evaluar el rango — probar que el orden
   documentado (forma→firma→ventana→rango→nonce) se respeta, no solo que el resultado final da lo
   mismo.
