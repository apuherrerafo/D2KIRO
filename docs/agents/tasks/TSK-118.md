## Contexto

Auditoría previa (misma sesión) confirmó que el repo no tenía ningún pipeline de CI/CD: sin
`.github/workflows/`, sin Husky/lint-staged, sin git hooks locales activos. Lo único parecido a un
gate (`scripts/verify-simplicity.sh`) solo corre dentro de sesiones de Claude Code (hooks
`PostToolUse`/`SubagentStop` de `.claude/settings.json`) -- nunca en un `git push` normal desde la
terminal, y nunca en un PR de GitHub porque no hay ningún workflow remoto que lo dispare ahí.

## Cambios

- **`.github/workflows/ci.yml`**: matriz paralela de 3 targets (`engine`, `web`, `root`/`scripts`),
  cada uno con su propio `bun install` (monorepo sin bun workspaces -- 3 `bun.lock` independientes,
  ver hallazgo de la auditoría de CI). `oven-sh/setup-bun@v2` + cache de
  `~/.bun/install/cache` por hash de `**/bun.lock`. Job independiente `verify-simplicity` con
  `fetch-depth: 100` (necesita historia real para el merge-base contra la rama base del PR).
  `root`/`scripts` no corre `tsc`/`lint` -- no tiene `tsconfig.json` ni ESLint propio, no se
  inventa una herramienta nueva solo para completar la matriz.
- **`scripts/verify-simplicity.sh`**: base de comparación adaptativa. Local (sin cambios de
  comportamiento -- sigue comparando contra `HEAD`, el uso real que ya tenían las sesiones de
  Claude Code). CI (`GITHUB_ACTIONS=true`): con `GITHUB_BASE_REF` (evento `pull_request`), hace
  fetch dirigido de la rama base y usa el merge-base real (`git merge-base origin/$GITHUB_BASE_REF
  HEAD`) -- nunca la rama base a secas, para no arrastrar commits ajenos que la rama destino
  sumó después de abrirse el PR. Sin `GITHUB_BASE_REF` (push directo) usa `HEAD~1`. Los tres
  caminos probados explícitamente: merge-base real (`GITHUB_BASE_REF=master`, fetch real contra
  `origin` completado, merge-base resuelto a `4106cfa...`), rama base inalcanzable (fallback a
  `HEAD~1` sin romper), y push directo. `chmod +x` aplicado.
- **Husky 9 + lint-staged** (`husky`/`lint-staged`, devDependencies de la raíz -- bypass total por
  categoría, Governance 2.0): `"prepare": "husky"` en `package.json` raíz, `bunx husky` corrido
  (`core.hooksPath=.husky/_`, mecanismo real de la v9 verificado leyendo `node_modules/husky/
  index.js` antes de asumir cómo funciona -- ya no es el shim `. _/husky.sh` de v8, deprecado).
  `lint-staged.config.js`: `apps/web/**/*.{ts,tsx}` corre ESLint real (el único linter del
  proyecto); `apps/engine/**/*.ts` corre `tsc --noEmit` de proyecto completo (función que ignora
  los filenames -- un chequeo de tipos por archivo aislado no es confiable sin el resto del
  proyecto cargado); `scripts/**/*.ts` corre su propia suite de tests (sin linter ni
  `tsconfig.json` propio, es el único chequeo real que existe hoy ahí). `.husky/pre-commit` corre
  `bunx lint-staged`. `.husky/pre-push` corre la batería completa de cada subapp (bun test + tsc
  para engine; bun test + tsc + lint para web; bun test para scripts) sin importar qué archivos
  cambiaron -- un tipo roto en un archivo puede romper otro que nadie tocó en el commit.
- **Hallazgo real durante la verificación, corregido en el mismo ticket**: `bun run lint` en
  `apps/web` tenía **1 error preexistente** (no introducido por esta sesión, confirmado con `git
  log`/`git status` -- el archivo no aparecía en ningún diff sin commitear, viene de TSK-074) en
  `components/draft-timer/DraftTimer.tsx:34`: `Date.now()`/`new Date()` llamados en el cuerpo del
  render, violando la regla `react-hooks/purity` (React 19). Nadie lo había notado porque ESLint
  nunca corrió como gate obligatorio en ningún lado -- exactamente el tipo de brecha que este
  ticket cierra. Corregido moviendo el cálculo de `startedAtMs` dentro del inicializador perezoso
  de `useState` (ya existente en la línea siguiente, mismo patrón) -- cero cambio de
  comportamiento, la función solo deja de invocarse en cada render. `bun run lint` pasa a 0
  errores (2 warnings preexistentes, no bloqueantes, quedan sin tocar -- fuera de alcance).

## Verificación

- `bash scripts/verify-simplicity.sh` (local): verde.
- `GITHUB_ACTIONS=true bash scripts/verify-simplicity.sh` (push directo, sin `GITHUB_BASE_REF`):
  verde, usa `HEAD~1`.
- `GITHUB_ACTIONS=true GITHUB_BASE_REF=master bash scripts/verify-simplicity.sh`: verde, fetch real
  contra `origin` completado, merge-base resuelto correctamente.
- `GITHUB_ACTIONS=true GITHUB_BASE_REF=this-branch-does-not-exist ...`: verde, cae a `HEAD~1` sin
  romper.
- `bunx lint-staged` corrido con un archivo real de cada glob (`apps/engine/src/signals/mix.ts`,
  `apps/web/features/random-draft-simulator/orchestrator.ts`, `scripts/sync-context.ts` con un
  marcador temporal, revertido después): las 3 tareas corrieron y terminaron ok.
  `.husky/pre-push` corrido directo de punta a punta: `apps/engine` 471/471 + tsc limpio,
  `apps/web` 180/180 + tsc limpio + lint 0 errores, `scripts` 9/9. `EXIT=0`.

## Fuera de alcance

Los 2 warnings preexistentes de ESLint (`NavBar.tsx` sin `next/image`, variable no usada en
`bot-drafter.ts`) -- no bloquean, quedan documentados, no se tocan en este ticket. Puntos 3-5 de la
lista de Codex sobre el simulador (contrato de evidencia estructurada, separar observado/hipótesis,
gate de arquitectura de contratos) siguen sin empezar, no forman parte de este ticket.
