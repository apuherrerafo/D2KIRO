## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5, `docs/specs/SPEC.md` §12.6, §12.11, §12.15-A
y §12.17 (ticket 9 de Bloque B). Depende de TSK-097 (contrato del token, para que la firma coincida
en los dos lados) y TSK-100 (`lib/session.ts`). **Este es el ticket donde el Basic Auth compartido
deja de existir** — por eso va junto con el guard fail-closed en el mismo diff, mismo criterio que
usó el proyecto quando `SITE_ACCESS_*` se introdujo originalmente (hallazgo de Sentinel en el
primer `/castoff`: un guard que falla abierto si falta el secreto es peor que no tener guard).

**Corrección real de `/blueprint`, no un detalle menor (SPEC.md §12.15-A)**: `fetchBaseQuery`/
`prepareHeaders` de `lib/engine-api.ts` **no puede** firmar el token — el navegador no tiene ni
puede tener `INTERNAL_AUTH_SECRET`, y no puede leer la cookie `httpOnly`. El token se acuña **acá**,
en `proxy.ts` (que corre en runtime Node, servidor), y se inyecta como header hacia el destino del
rewrite.

## Alcance — 3 archivos

### 1. `apps/web/proxy.ts`
Se retiran `isValidBasicAuth` y el uso de `SITE_ACCESS_USER`/`SITE_ACCESS_PASSWORD` (el borrado
final de esas funciones/variables es TSK-106 — acá solo se deja de *usarlas* en el flujo de
autorización, sin tocar código no relacionado). Nueva lógica: leer la sesión de `iron-session`
(TSK-100); sin sesión válida, redirige a `/login` (salvo `/login`, `/api/auth/*`, `/healthz`). Con
sesión válida y la request va hacia el rewrite de `apps/engine`: acuña el `x-account-token` (mismo
contrato de TSK-097) con `accountId` de la sesión, y lo inyecta vía
`NextResponse.next({ request: { headers } })`.

**Criterio de aceptación 8 de SPEC.md §12.14 — verificar esto primero, antes de construir el resto
del ticket**: confirmar contra el binario real de Next 16 instalado que un header inyectado en
`proxy.ts` efectivamente llega al destino externo de un `rewrite`. Si no llega, aplicar el Plan B
documentado en SPEC.md §12.11 (Route Handler `app/engine/[...path]/route.ts` en vez de inyección en
el proxy) — **no asumir que el mecanismo funciona sin esta verificación**, es justo el tipo de
supuesto que ya falló una vez en este proyecto (`middleware.ts` crasheando en Edge Runtime, TSK-039).

### 2. `apps/web/lib/account-token.ts` (nuevo)
El acuñado — espejo exacto del contrato de verificación de TSK-097 (`server/account-token.ts` en
`apps/engine`), firmando en vez de verificando. **Usa el mismo vector de prueba de §12.6** — la
prueba de este archivo debe producir exactamente la misma firma que la prueba de TSK-097 para el
mismo input (criterio 9 de §12.14, candado compartido entre procesos).

### 3. `scripts/start-railway.sh`
El guard existente sobre `SITE_ACCESS_*` se reemplaza por: abortar si falta `SESSION_SECRET`,
`INTERNAL_AUTH_SECRET`, o `PUBLIC_BASE_URL` — mismo mecanismo (fail-closed, el proceso no levanta),
mismo motivo original.

## Casos a probar
1. Sin sesión, cualquier ruta salvo `/login`/`/api/auth/*`/`/healthz` redirige a `/login`.
2. Con sesión válida, una request hacia el rewrite de `apps/engine` lleva el header
   `x-account-token` con una firma verificable por `verifyAccountToken` (TSK-097) usando el mismo
   `INTERNAL_AUTH_SECRET`.
3. El vector de prueba de §12.6 produce la misma firma en `lib/account-token.ts` que en
   `server/account-token.ts` (TSK-097) — prueba cruzada explícita, no solo "cada uno pasa su propia
   prueba por separado".
4. `start-railway.sh` sin `SESSION_SECRET`/`INTERNAL_AUTH_SECRET`/`PUBLIC_BASE_URL` → el proceso
   aborta, no levanta el motor con el guard fallando abierto.
5. **Verificación contra el binario real** (criterio 8): un test de integración (o verificación
   manual documentada en el ticket al cerrarlo) confirma que el header llega al destino del rewrite
   en un `next dev`/`next start` real, no solo en una prueba unitaria mockeada.
