## Contexto

SPEC.md §15.4.4. El usuario no inventa 30 estados de cero: la herramienta **propone** (no etiqueta)
los más informativos, ordenados, y el usuario cura sobre eso (TSK-206).

## Alcance

`scripts/eval/propose-golden-cases.ts` — determinista, produce una lista ordenada de ~30
candidatos. Criterios:

1. **Cobertura de estratos**: cuota por `decisionContext` (4) × estrato temático (7 de
   §15.4.4) — prioriza llenar celdas vacías.
2. **Desacuerdo entre baselines**: estados donde `positionFitOnly`, `patchMetaOnly` y `v6Full`
   (TSK-200) producen Top-5 con bajo Jaccard entre sí (TSK-198). Ahí el etiquetado humano
   discrimina; donde todos coinciden, no aporta.
3. **Fallos históricos**: estados de replay donde `v6Full` rankea el pick profesional real **fuera
   del Top-10**.
4. **Escenarios sintéticos** (`eval/scenarios/*.json`) para estratos que el corpus no cubre bien —
   construidos desde `hero-counters.json` (un hard counter curado ya revelado) y
   `hero-positions.json` (role scarcity forzada). Se generan acá, versionados.

Salida (`eval/scenarios/proposal-<timestamp>.json`, ignorado por git salvo que el usuario lo
promueva): por candidato → `state`, `decisionContext`, `strata` asignado, `razonElegido`, y el
**Top-6 actual de V6** como punto de partida para la etiqueta.

## Criterios de aceptación

1. Con fixtures (replays + baselines simulados), la herramienta devuelve una lista ordenada
   determinista con los 4 criterios representados y el estrato de cada candidato.
2. Dos corridas con la misma entrada → misma propuesta (byte a byte).
3. Los escenarios sintéticos generados pasan el type-guard de `DraftState` y el loader de TSK-199.
4. `git diff --name-only` no toca `apps/`. Ninguna prueba abre SQLite real.

## Fuera de alcance

Etiquetar (trabajo humano, TSK-206). Congelar el baseline (TSK-202).
