## Contexto (ticket autocontenido)
Proyecto: dota2coach. Segundo de los 3 tickets de "reporte de QA" (ver TSK-050 para el contexto
completo del origen y la decisión de producto). Depende de **TSK-050** (la tabla `draft_feedback`
ya tiene que existir).

`apps/engine/src/server/app.ts` ya tiene el patrón exacto a seguir: endpoints de solo lectura sin
auth para datos locales (`GET /api/heroes`, `GET /api/meta/hero-stats`), y endpoints de escritura
transaccional con validación de borde (`PUT /api/hero-pool`).

## Alcance

### `POST /api/session/:id/feedback`
- Recibe `{ comment: string, draftState: unknown, suggestions: unknown | null }` en el body.
- **Validación de borde, todo es input externo**: `comment` string no vacío, máximo 4000
  caracteres (evita un reporte gigante por error de copiar/pegar, no una defensa contra ataque --
  el motor solo escucha en `127.0.0.1`). `draftState` debe ser un objeto (`typeof === "object" &&
  !== null`), no se valida su shape interno campo por campo -- ya viene validado del lado de
  `apps/web` por el propio store de Zustand, y forzar un segundo esquema completo acá sería
  redundante. `suggestions` igual, pero puede ser `null`.
- Inserta una fila en `draft_feedback` (Drizzle, parametrizado) con `session_id` = el `:id` de la
  URL, `created_at` = ahora (ISO-8601).
- Responde `202` con `{ accepted: true }` en éxito, `400` con `{ accepted: false, reason: "..." }`
  si la validación falla -- nunca un 500 por un body malformado.
- **Sin `x-capture-token`** -- mismo criterio que `/api/session/manual`, es una escritura local
  desde `apps/web`, no del capturador.

### `GET /api/feedback`
- Solo lectura, sin auth (mismo criterio que `GET /api/heroes`).
- Devuelve todos los reportes, más nuevos primero (`orderBy(desc(draftFeedback.createdAt))`),
  cada uno con sus 5 columnas ya parseadas (los campos JSON como objetos, no como texto plano) --
  existe para que una sesión de Claude Code futura pueda leerlos directo con `curl` sin tener que
  tocar la SQLite a mano.
- Sin paginación en esta primera vuelta -- el volumen esperado es "algunos reportes por sesión de
  QA", no miles.

## Fuera de alcance
- El schema/migración (ya hecho, TSK-050).
- La UI que llama a `POST /api/session/:id/feedback` (TSK-052).
- Cualquier endpoint de borrado/edición -- inbox append-only, igual que `journal.md`.

## Aceptación
- `POST /api/session/:id/feedback` con un body válido inserta la fila correcta, verificable con
  una lectura directa después.
- `POST` con `comment` vacío o mayor a 4000 caracteres devuelve `400`, no inserta nada.
- `POST` con `draftState` ausente o no-objeto devuelve `400`, no inserta nada.
- `GET /api/feedback` devuelve los reportes insertados, orden más nuevo primero, con `draftState`/
  `suggestions` como objetos JSON reales (no strings escapados dos veces).
- `bun test` sin regresiones, `tsc --noEmit` limpio, `verify-simplicity.sh` PASS.
