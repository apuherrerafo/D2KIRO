## Contexto (ticket autocontenido — Codex no lee journal.md ni architecture.md)
Proyecto: dota2coach, motor de sugerencias de picks/bans para Dota 2. `apps/engine` es un
servidor Bun con SQLite + Drizzle ORM. Fase 1 (MVP) ya está completa: tablas `heroes`,
`hero_patch_stats`, `hero_matchups`, `meta_sync`, `settings` ya existen (`apps/engine/src/db/
schema.ts`). Esta es la primera pieza de fase 1b (personalización de hero pool): el usuario puede
guardar hasta 5 héroes con los que juega cómodo, a mano o calculados desde su historial de
OpenDota, para que el motor de sugerencias los tenga en cuenta.

Este ticket es la excepción documentada de `CLAUDE.md`: schema + migración cuentan como **una
sola unidad lógica**, aunque toquen más de 1 archivo. Marca `simplicity_exception: true` en el
frontmatter de este ticket antes de commitear si el conteo real lo amerita.

## Esquema exacto a implementar (Drizzle, SQLite)

Tabla nueva `hero_pool`:

| Columna | Tipo | Nota |
|---|---|---|
| `hero_id` | integer PK, FK → `heroes.id` | Un héroe no puede estar dos veces en el pool |
| `source` | text `'manual' \| 'calculated'` | Procedencia honesta, mismo principio que `CaptureSource` en el contrato de eventos de draft |
| `personal_winrate` | real, nullable | `null` = añadido a mano sin winrate conocido |
| `personal_games` | integer, default `0` | |
| `updated_at` | text ISO-8601 | |

Claves nuevas en la tabla `settings` (ya existe, sin cambio de esquema — son filas, no columnas):
`steam_account_id` y `personal_baseline_winrate`.

**No crear tabla de historial de partidas** — solo se persiste el agregado (héroe → winrate/
partidas), nunca las partidas individuales. Fuera de alcance de 1b.

## Reglas duras
- Toda columna/query vía Drizzle. Cero SQL concatenado.
- Migración generada con el CLI de Drizzle (`npx drizzle-kit generate`), no escrita a mano.
- Sin dependencias nuevas — el driver de SQLite y Drizzle ya están decididos. Si hace falta algo
  más, no lo añadas, repórtalo.
- Máximo 5 filas en `hero_pool` por diseño (el límite se aplica en la capa de escritura, TSK-020 —
  este ticket solo define el esquema, no valida el conteo).

## Aceptación
- `bun run` de la migración crea la tabla `hero_pool` con los tipos y la PK exactos de la tabla de
  arriba, más las dos claves nuevas usables en `settings` (sin migración de esquema, son solo
  filas — verificar con un insert/select de prueba).
- Una query de ejemplo (insert + select) contra `hero_pool` funciona parametrizada vía Drizzle.
