## Diseño
- Aplica solo en modo "Velocidad" del simulador -- en "Paso a paso" el usuario controla el ritmo
  a mano, no hay espera que cronometrar.
- Aplica solo a eventos `hero_picked` -- los `hero_banned` ya no esperan (TSK-034, Tarea A), nada
  que mostrar ahí.
- `runSimulatorPlayback` gana un callback opcional `onWaitStart(waitMs)`, invocado justo antes de
  esperar cada evento con `delayMs > 0` -- puramente aditivo, sin cambiar el comportamiento
  existente cuando se omite (regresión cero, mismos tests actuales sin tocar).
- `DraftTimer` (componente nuevo): número de segundos + barra horizontal que se vacía, con su
  propio `useEffect`/`setInterval` interno -- es un caso legítimo de sincronización con tiempo
  real, no un cálculo derivable en render. Remonta por `key` en cada wait nuevo (evita el bug de
  no reiniciar cuando dos esperas consecutivas tienen el mismo `delayMs`, ej. picks de 3000ms
  seguidos en captainsMode).
- Vive dentro de `DraftSetupPanel`, reemplazando el texto "Reproduciendo el draft..." mientras hay
  una espera activa -- mismo lugar donde ya vive el estado del simulador, sin tocar `DraftView.tsx`
  ni `DraftBoard.tsx`.

## Fuera de alcance
- Timer para un draft real (Overwolf/manual) -- depende del spike, no confirmado.
- Modo "Paso a paso".
- Cualquier lógica de banco de reserva o tiempo por posición (tabla de turnos de Valve sigue fuera
  de alcance del proyecto).

## Aceptación
- En modo Velocidad, mientras el simulador espera antes de un `hero_picked`, se ve un contador
  regresivo (segundos + barra) que llega a 0 justo cuando se postea el evento.
- Dos picks consecutivos con el mismo `delayMs` (ej. 3000ms) reinician el timer correctamente en
  cada uno -- nunca se queda "pegado" mostrando el número del anterior.
- Sin tocar el callback (comportamiento por defecto), `runSimulatorPlayback` se comporta exacto
  igual que antes -- las pruebas existentes de `simulator.test.ts` pasan sin modificarse.
