## Contexto (ticket autocontenido)
Proyecto: dota2coach. Origen: `/blueprint` de Fase 5, `docs/specs/SPEC.md` §12.10 y §12.17 (ticket 5
de Bloque A). Depende de TSK-095 (`hero_pool` con `accountId`), TSK-096 (`buildMetaSnapshot`
multi-cuenta) y TSK-097 (`verifyAccountToken`). Este es el ticket donde `apps/engine` deja de
confiar ciegamente en cualquier request — cierra el hallazgo real de la auditoría previa a esta
fase: `GET /api/settings` devuelve todo sin filtrar a cualquiera que llegue al puerto.

## Alcance — 3 archivos

### 1. `apps/engine/src/server/require-account.ts` (nuevo, helper)
```ts
export function requireAccount(
  req: Request, secret: string, now: () => number, nonceStore: NonceStore, db: Db,
): { ok: true; accountId: AccountId } | { ok: false; response: Response };
```
Envuelve `verifyAccountToken` (TSK-097) + una verificación adicional: si el token es válido pero
`accountId` no existe en `accounts`, responde `401 { error: "unknown_account" }` — **salvo** en
`POST /api/account`, la única ruta que acepta un token de una cuenta que todavía no existe (la usa
el callback de login para crear la cuenta la primera vez). El `response` ya viene con el `401` y el
cuerpo tipado correcto para cada uno de los 5 errores de §12.10 — el llamador solo hace
`if (!result.ok) return result.response`.

### 2. `apps/engine/src/server/routes/account.ts` (nuevo)
`GET /api/account` (token) → `{ steamAccountId, personalBaselineWinrate, createdAt }` de la cuenta
del token. `POST /api/account` (token de cuenta inexistente aceptado) → `INSERT ... ON CONFLICT DO
NOTHING` en `accounts`, idempotente.

### 3. `apps/engine/src/server/app.ts` + `apps/engine/src/server/routes/hero-pool.ts`
- `GET/PUT /api/hero-pool`, `POST /api/hero-pool/calculate`, `POST /api/meta/sync` ganan
  `requireAccount` delante. `calculate` **pierde el campo `accountId` del cuerpo** — el contrato
  queda en `{ days?: number }`, el Steam32 sale del token.
- `calculationInProgress` (booleano por proceso en `hero-pool.ts`) pasa a `Set<AccountId>` — un
  cálculo en curso bloquea solo a su propia cuenta con `409`.
- `GET`/`PUT /api/settings` se **retiran** de `app.ts` (P3) — mover el borrado de
  `getAllSettings`/`upsertSetting` en `queries.ts` al ticket de limpieza (TSK-106), no acá (nunca
  mezclar retiro de ruta con borrado de código muerto en el mismo diff, criterio TSK-047).
- `GET /api/health` gana un campo `authMode: "multi_tenant"` (o el nombre que ya use el proyecto
  para distinguir modos, si existe) — no expone ningún dato de cuenta, solo el modo activo.
- `computeSuggestionsForState` sigue pasando `null` en este ticket (TSK-099 lo conecta a la cuenta
  real de la sesión de WebSocket) — el `// TSK-098: ...` de TSK-096 se resuelve acá **solo** para el
  camino HTTP directo si existe uno; si el único consumidor real es el WS, dejar el comentario
  apuntando a TSK-099 en su lugar.

## Casos a probar
1. `GET /api/hero-pool` sin header → `401 missing_account_token`.
2. `GET /api/hero-pool` con token de cuenta A devuelve solo el pool de A, aunque exista pool de B
   (contra la DB real de pruebas con dos cuentas, no un mock).
3. `POST /api/hero-pool/calculate` con `accountId` en el cuerpo → el campo se ignora (no rompe, no
   se usa) — el Steam32 real sale exclusivamente del token.
4. Dos cálculos concurrentes de cuentas distintas: ninguno bloquea al otro. Dos cálculos de la
   misma cuenta: el segundo responde `409`.
5. `GET`/`PUT /api/settings` responden `404` (ruta retirada), no `401`.
6. `POST /api/account` con token de una cuenta inexistente → la crea (`201` o `200`, definir);
   segunda llamada idéntica → no falla, no duplica.
7. Ningún cuerpo de error de los 5 tipos de §12.10 incluye el valor del `accountId`.
