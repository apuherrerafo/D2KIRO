## Contexto

QA de Fase 8 en el simulador reveló que el Copilot **trae casi siempre las mismas
recomendaciones** y **no respeta el rol elegido ni el hero pool**. Causa raíz (auditoría del flujo
completo, 2026-08-29): el `POST /api/suggestions/preview` que hace
`apps/web/features/random-draft-simulator/use-random-draft-session.ts` **nunca manda**
`targetPosition` ni `usePersonalPool`, y no adjunta `x-account-token`. Sin eso:

- `position_fit` no discrimina por el rol que el usuario quiere; `candidatePool` no filtra por
  posición (`mix.ts` línea 313: `targetPosition === undefined` → sin filtro).
- `hero_pool_fit` queda `applicable: false` siempre → el pool no influye nada.
- En picks tempranos, sin enemigos revelados (`counter` null) y sin intención puesta
  (`archetype_fit` null), la única señal con peso es `patch_meta` → el top-N es "los más pickeados
  del parche", casi idéntico en cada draft.

**El motor ya está listo**: `handleSuggestionsPreview` (`app.ts:160`) acepta `targetPosition` y
`usePersonalPool`, hace `requireHttpAccount(request)` cuando `usePersonalPool && !teamOpening`, y
pasa todo a `computeSuggestionsForState` → `buildSuggestions`. Hay un comentario en
`use-random-draft-session.ts:442` que ya dice *"El simulador pide su preview autenticado (pool +
rol + diversidad)"* — la intención estaba, el código quedó a medias. Cero cambios en el motor.

Precedente del token: `use-copilot-pro-drafter.ts:40` ya hace
`fetch("/api/auth/engine-token", { credentials: "same-origin", cache: "no-store" })` → `.json()` →
`{ token }` y lo manda como header `x-account-token`.

Hay una sola llamada al preview (`refreshPendingPickPreview`); `retryPreview` y
`setArchetypeIntent` reusan ese mismo camino.

## Alcance — solo `apps/web/features/random-draft-simulator/use-random-draft-session.ts`

1. Helper `fetchEngineToken(): Promise<string | null>` — `fetch("/api/auth/engine-token",
   { credentials: "same-origin", cache: "no-store" })`, devuelve `token` o `null` (best-effort,
   nunca lanza; si el usuario no tiene sesión, degrada sin romper el preview).
2. En `refreshPendingPickPreview`, antes del `fetch` del preview:
   - `const teamOpening = previewState.picks.radiant.length === 0 && previewState.picks.dire.length === 0;`
   - `const token = teamOpening ? null : await fetchEngineToken();`
   - body gana `targetPosition: current.config.playerPosition` (el motor ignora `undefined` y el
     caso `teamOpening`).
   - body gana `usePersonalPool: token !== null && !teamOpening` (sólo `true` si hay token —
     mandar `usePersonalPool: true` sin token da `401` y tira todo el preview).
   - headers ganan `...(token ? { "x-account-token": token } : {})`.
3. Nada más. Sin cambios de store, sin nuevos endpoints, sin tocar el WS.

## Criterios de aceptación

1. `bunx tsc --noEmit` limpio en `apps/web`. `bun test apps/web` verde, cero regresión.
2. Con sesión activa y `playerPosition` elegido, el `POST /api/suggestions/preview` lleva
   `targetPosition` + `usePersonalPool: true` + header `x-account-token`. Verificado con el test de
   integración de `use-random-draft-session` (el `FakeEngine` registra el body y los headers).
3. Sin sesión (token `null`) → el preview se manda **sin** `usePersonalPool` ni header, sigue
   funcionando (degradación), `targetPosition` igual viaja.
4. En `teamOpening` (draft vacío) → no se pide token, no se manda `usePersonalPool` (coherente con
   la guarda del motor).
5. QA manual en `/simulator`: elegir midlane → el Copilot filtra a héroes de mid y prioriza los
   del pool (`hero_pool_fit` aparece con valor en el desglose, ya no "no aplica").

## Fuera de alcance

Tocar el motor (ya acepta todo). El bot del simulador (scoring propio, no cambia). El pipeline
Pro-Drafter dark. Regenerar `draftSeed` automático por draft (es decisión de UX aparte — si el
usuario reusa el mismo seed ve el mismo draft, es by-design).
