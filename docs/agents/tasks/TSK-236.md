## Contexto

`TSK-235` (PR #16) habilitó el CI canónico sobre PRs a `staging/private-beta-1`. El trigger
funciona, pero el primer run (`37056937133`, head `0aa7ca4`) dejó `test (root)` en rojo con dos
fallas **previas** de staging — pruebas de `scripts/` que entraron sin CI y sólo pasaban en la
máquina Windows del desarrollador. `r1-certification` queda `skipped` por `needs:`. No son
regresiones de `TSK-235`; este ticket las arregla sin ensanchar `TSK-235` (que sigue siendo sólo el
trigger y queda desbloqueado por éste).

Integración apilada: rama `ci/root-scripts-linux-portability` creada desde el head de PR #16
(`0aa7ca4`), PR hacia `ci/staging-pr-trigger`. El workflow sólo dispara en PRs a
`master`/`staging/private-beta-1`, así que la prueba Linux real es el CI de PR #16 una vez que este
cambio llega a su rama.

## Las dos fallas (evidencia roja)

1. **`scripts/dev-mvp-config.test.ts`** — esperaba el literal Windows
   `C:\repo\apps\engine\data\custom.sqlite`. `resolveMvpDatabasePath` usa `node:path`, que resuelve
   con la semántica del SO anfitrión. CI (Linux): `Received:
   "/home/runner/work/D2KIRO/D2KIRO/C:/repo/apps/engine/data/custom.sqlite"`. Reproducido local en
   Linux real (WSL2, Bun 1.4.2 linux-x64): mismo resultado. **Bug de portabilidad de la prueba**,
   no del código.
2. **`scripts/dev-mvp-db.test.ts`** — `ensureManualMvpDatabase` corre la migración **real**
   (`bun run src/db/migrate.ts`, `cwd: apps/engine`). El job `test (root)` sólo instala las
   dependencias de la raíz. CI: `error: engine database migration failed`. Reproducido local en un
   worktree limpio con sólo `bun install` de la raíz: la migración falla con
   `Cannot find module 'drizzle-orm/bun-sqlite/migrator'`. **Falta de entorno del job**, no de la
   prueba.

## Alcance (mínimo)

- **A.** `scripts/dev-mvp-config.test.ts`: la prueba verifica la invariante semántica — una
  `ENGINE_DB_PATH` relativa (`data/custom.sqlite`) se resuelve desde `<repo>/apps/engine` con la
  semántica de rutas del SO anfitrión — con una raíz absoluta derivada del SO y el esperado armado
  con `node:path`. En Windows la raíz sigue siendo `C:\repo` (mismo literal que antes). Producción
  (`dev-mvp-config.ts`) **no cambia**.
- **B.** `.github/workflows/ci.yml`: un paso explícito, análogo al de `web`, que instala las
  dependencias de `apps/engine` (`bun install --frozen-lockfile`) **sólo** cuando
  `matrix.target == 'root'`, antes de las pruebas de `scripts/`. No se debilita
  `dev-mvp-db.test.ts`, no se mockea la migración, no se duplican dependencias del motor en la raíz,
  no se agrega ningún skip condicional.

**No cambia**: comandos de prueba, estructura de la matriz, secretos, permisos, triggers,
`verify-simplicity`, `intelligence-ci`, `r1-certification`, despliegue de Railway, `master`.

## Criterios de aceptación

1. `scripts/dev-mvp-config.test.ts` pasa en Windows **y** en Linux (WSL2 local + runner de CI).
2. `scripts/dev-mvp-db.test.ts` sin cambios; pasa en un checkout limpio una vez instaladas las
   dependencias de `apps/engine`; sigue fallando (rojo) sin ellas.
3. `bash scripts/verify-simplicity.sh` en verde.
4. En PR #16, con este cambio en su rama: `test (engine)`, `test (web)`, `test (root)`,
   `verify-simplicity`, `intelligence-ci` y `r1-certification` en verde.
